## 总体判断

dustoff 是一个个人收藏内容处理工具：把抖音收藏视频变成可回溯、可检索的 Markdown 笔记，供 Obsidian 使用。

目前处于「三段流程已有实现和小样本实跑，笔记质量尚未验收，自动化尚未接入」阶段。基础结构适合当前个人使用规模，无需先重构为服务或引入复杂框架。下一步应先验收笔记，同时补齐日常编排的恢复缺口，再扩大处理量和接定时。

本轮基于 Git 提交 `8ceb352`、源码、现有文档及本机账本进行复核。仅整理文档；没有运行真实扫描、下载或付费 API，没有改动正式账本、媒体和笔记。历史文档中的速度、费用和收藏总量是当时的样本或估算，本轮未重新测量。

## 目标、边界和流程

输入是抖音收藏列表；主要中间产物是视频和转写稿；最终输出是一条视频对应一篇笔记。跨视频去重、知识融合、知识图谱尚未进入当前处理链路。

```text
收藏列表 → 扫描与下载 → mp4 → 云端 ASR → txt → LLM 提炼 → Markdown / Obsidian
              │                  │                 │
              └──────────────── SQLite 账本 ────────┘
```

| 组成 | 作用与边界 |
|---|---|
| `sync.mjs` | 扫描收藏，导入账本，筛出 pending，再下载。全量扫描才进行取消收藏对账 |
| `extract.mjs` | 将已下载媒体转成文字；承担外接盘归档、文字备份和本地过期媒体清理 |
| `notes.mjs` | 消费转写稿，生成笔记；支持独立试跑和按提示词版本重新提炼 |
| `run.mjs` | 日常串行编排，复用提取和提炼函数；存量仍可按三段分别处理 |
| `scripts/ledger.mjs` | 记录素材身份、处理状态、产物路径和重试计数，是流程衔接的核心 |
| `scripts/stage.mjs` | 公共锁、日志、运行记录、通知和退出码 |
| `scripts/get_collection.mjs` / `download.mjs` | Chrome 登录态采集与媒体下载零件 |
| `scripts/get_meta.mjs` / `fetch.mjs` | 旧单条链接流程，包含本地 whisper 路径，不属于当前批量主线 |

正常状态是 `pending → downloaded → transcribed → extracted`；另有 `skipped`、`failed`、`removed` 三种分支状态。需要 OCR 补料的条目会进入 `skipped` 并附带 `needs_ocr=1`。

代码共 15 个 `.mjs` 文件、4005 行，零 npm 依赖。主要依赖 Node 内置 SQLite、Chrome、curl/file、ffmpeg 和两个云端模型接口。代码、运行数据（`~/.dustoff`）、Obsidian 笔记分开存放；本机配置指向 T7 外接盘用于媒体归档和文字备份。

## 已确认的流程缺口

以下问题经过源码核对和临时隔离数据复现。验证时使用模拟扫描器、下载器及独立数据库，没有连接外部服务。

### 1. 日常入口不会自动续跑中间状态，优先修复

`run.mjs:285` 使用 `pendingAmong()` 筛选扫描结果，该函数只返回 `pending`。已下载、已转写条目即使出现在本轮收藏列表，也被排除；只有显式 `--no-scan` 才会查出这两种状态。

复现：准备 pending、downloaded、transcribed、failed 各一条。默认扫描预览仅选出 pending；`--no-scan --dry-run` 才选出 downloaded 和 transcribed。

影响：某条下载完成后转写失败，或转写完成后提炼失败，第二天普通 `node run.mjs` 不会自动续跑。当前已有的 27 条待转写和 12 条已转写积压也不会因默认入口而得到处理。文档中「下一轮从断点接着走」的承诺尚未完整实现。

建议：日常候选集合应合并本轮可下载条目与账本中的 downloaded/transcribed 积压，按视频 ID 去重，再应用本轮数量限制。pending 仍需新鲜播放地址，中间状态则使用已有产物。

### 2. 日常下载失败会重复累计次数

`run.mjs:153` 先调用 `importDownload()`；下载结果为 failed 时，账本已将 attempts 加一。随后主循环捕获异常，再于 `run.mjs:335` 调用 `markFailed()`，又加一次。

复现：同一条模拟下载失败，第一轮 attempts 变成 2，第二轮变成 4 并进入 failed。配置默认上限为 3，实际只经历两轮失败便放弃。

建议：明确失败计数由哪一层负责，一轮单条下载失败仅登记一次；保留各独立入口的一致语义。

### 3. 待 OCR 的媒体从归档范围中消失

`scripts/ledger.mjs:370` 的归档查询仅选 transcribed/extracted。提炼判缺料后，条目变为 skipped，便不再满足归档条件。日常入口恰好在提炼之后统一归档，因此这类素材会遗漏。

复现：一个 transcribed 条目原本出现在归档候选中；调用 `markSkipped(..., 'need_ocr', { needsOcr: true })` 后，归档候选为空。

影响：后续 OCR 需要的视频留在本地，插回外接盘也不会被自动补归档。目前清理查询同样排除了 skipped，因此这条问题表现为归档遗漏和本地滞留，不是已证实的自动删除。

建议：归档资格依据素材和转写是否已完成，涵盖等待 OCR 的条目；清理仍需独立保留其原料保护规则。

### 4. `extract --force` 的文档含义与执行对象不同

README 将 `node extract.mjs --force` 描述为重试 failed；实际 `extract.mjs:571` 选择的是 transcribed。

复现：同一隔离库中存在 failed 和 transcribed，`extract.mjs --force --dry-run` 只选择已转写条目。

影响：按文档操作可能重做已经付费的转写，却没有处理目标失败条目。应先明确「失败重试」与「强制重转」各自的命令和选取规则，再同步文档；修改前先用预览确认对象。

### 全量启动前新增的关键问题

**1. 当前 `--init` 实际仍下载到内置盘。**

本机配置有 `DUST_MEDIA=~/.dustoff/media` 和 `DUST_EXTERNAL=/Volumes/T7`，但没有 `DUST_MEDIA_INIT`。`sync.mjs:85–100` 的配置优先级先尝试 `_INIT`，未配置就取普通 `DUST_MEDIA`，外接盘目录只是最后的默认值。因此本轮计算出的有效初始化参数是：

```text
媒体目录：/Users/enna/.dustoff/media
扫描条数：99999
```

这意味着直接运行 `node sync.mjs --init` 会在当前未插 T7 时仍尝试全量下载到内置盘。启动前至少应显式配置 `DUST_MEDIA_INIT=/Volumes/T7/dustoff-media`，更完整的修复是让初始化路径选择与文档承诺一致，并验证实际挂载设备及容量。本轮未改配置。

**2. 空间阈值没有阻止下载的作用。**

`DUST_MIN_FREE_GB=5` 只在 sync/run 收尾时触发通知。开始时打印容量，下载过程中不依据该阈值停止。把配置从 5 改成 15，也不会自动获得「剩余 15 GiB 时停下载」的行为。

需要补充启动前和下载过程中的检查：空间不足时停止新增媒体、保留当前进度；已有文字的提炼可以继续。建议本机初始采用剩余 15 GiB 停止新下载、本地工作媒体约 2 GiB 上限，再根据实际使用调整。这两个数是建议的运行策略，尚未实现，也不是系统强制要求。

**3. 现有归档与清理不能保证本地空间上限。**

日常 run 在整批处理完成后才归档，不是处理完一条就搬走一条。7 天清理只涵盖符合条件的已转写条目；待转写、失败以及待 OCR 条目不能靠它统一腾空间。外接盘长期未插时，已有设计也允许部分已转写视频到期删除，因此「以后插盘再归档」不保证原视频始终保留。

不能沿用旧存量规划中的「边下边删、磁盘峰值小于 1 GB」作为当前实现保证。历史全量估算约 16 GB（10 分钟时长上限）或约 29 GB（不限时长），均足以显著消耗本机当前余量；实际体积还需新扫描确认。

### 建议的存储分工

- 内置盘保留账本、转写稿、笔记及小规模工作缓存，避免在内置盘囤积全部历史视频。
- 全量视频直接写到挂载确认后的外接盘；日常视频采用有容量上限的本地缓存并及时归档。
- 针对当前小磁盘，优先采用「外接盘不在时暂停新视频下载，但继续处理已有文字」的保守模式；这是建议新增的策略，现有代码尚未执行。
- 正式启动前备份账本、转写稿与配置；账本使用 SQLite 备份机制生成一致快照，配置备份妥善保存 Key。现有自动文字备份不包含账本，账本丢失会影响去重、断点和产物定位。

### 启动准备与放行条件

1. 先用现有转写稿试写 3–5 篇，输出到独立试跑目录；检查忠实度、短稿不过度扩写、回源链接和中文文件名。此步无需插盘或新增视频。
2. 全量前接好 T7，核对真实挂载路径和可用容量，补齐初始化路径配置与下载空间硬限制；日常自动化前还要修复积压续跑、重复失败计数、OCR 归档和 force 语义。
3. 在无其他写入任务时做一致账本备份，保留转写稿、当前配置和试跑成品。
4. 进行小范围扫描，确认登录态；用一条本地视频验证 ASR，再用少量文字验证 LLM。Key 已填写、历史登录未到期均不能替代这一步。
5. 人工监督跑 5–10 条完整流程，核对笔记入库、归档后路径、磁盘前后占用及再次运行是否重复处理；验证盘未挂载和空间不足时能停止新下载。

| 日常扫描 | 从最新收藏向下，先查看最多 100 条；确认上次边界即可停止，未确认则继续分页 |
| 边界依据 | 作品 ID、收藏列表顺序与多条重叠参照；不能用发布时间、估算收藏时间或任意一个已知 ID 代替边界确认 |
| 新增入队 | 先把识别出的新增全部持久化，再推进扫描边界；不因处理额度耗尽丢弃新增 |
| 处理频率与额度 | 每天自动一次；当天累计最多处理 50 条，手动重跑或重启不重置当天额度 |
| 视频时长 | 超过 600 秒跳过；恰好 600 秒允许；未知时长先确认，不能直接放行 |
| 媒体容量 | 本地媒体缓存累计上限 1 GiB，包含视频、失败残留、待 OCR 原料与临时媒体 |
| 整盘保护 | 本机剩余空间低于 10 GiB，停止新增下载 |
| 视频清理 | 每日批次收尾统一删除 ASR 全部分段已完成、文字稿已可靠保存且非空、账本已记录成功的本地视频；不等笔记成功，不保留 7 天 |
| 外接盘 | 暂时停用全部交互：视频归档、文字备份、外接盘下载路径、挂载检查与相关提示；接盘不自动恢复 |
| 未完成事项 | 保留队列，后续按已有阶段续跑；达到数量或空间上限均允许当天少于 50 条 |

此处 1 GiB 是媒体缓存预算，文字、笔记、账本与日志另有少量占用，仍受整盘剩余空间保护。扫描 100 条只读取元数据，不等于下载 100 条。现有账本已经按批查询 ID，100/200 条通常只需一次数据库查询；主要优化点是减少浏览器分页和网络读取。

### 按顺序完成的全部待办

#### 1. 实现基线与扫描边界

- [ ] 增加明确的“只建基线”入口，保存最近 100 条的 ID、顺序及基线建立时刻；基线条目不变成 pending。普通重启不能自动重建基线。
- [ ] 日常扫描初始窗口设为 100；找到可靠重叠即停止，未找到则继续读取后续页。某条参照取消收藏时利用其他参照；仍无法确认边界时保留已有进度并提示，不把陌生历史全部当新增。
- [ ] 新增登记与边界推进保持一致，崩溃重跑也不能出现“边界已经推进但待办未保存”的遗漏。按作品 ID 去重；图集、超时长等明确跳过事项记录原因。

“从今天开始”落实为实际建立基线之后的新增，不追溯当天零点。初次建基线时已存在的最近 100 条同样不下载。

#### 2. 实现每日额度与跨轮续跑

- [ ] 持久化本机日期与当天参与处理的条目，所有正常处理入口共用每日 50 条额度；同日重启不能再获得 50 条。只在扫描阶段判断并跳过的超时长条目不占实际处理名额。
- [ ] 新增先全部登记，再从待办中取任务；例如 80 条新增先全记账，当天最多处理 50 条，其余 30 条留待后续。排队条目优先按等待顺序推进，避免旧待办长期得不到处理。
- [ ] 修复 F1：pending、downloaded、transcribed 均可按阶段继续，已成功阶段不重复下载或调用模型。过期的待下载地址能单独刷新，不要求再次扫到该条目才可恢复。
- [ ] 修复 F2：同一次下载失败只增加一次失败计数；区分临时失败、达到重试上限与主动跳过，避免永久无上限重试。

#### 3. 落实磁盘硬限制与运行时限

- [ ] 将 1 GiB 媒体上限与剩余 10 GiB 阈值做成真正的下载门槛；开始前、每条下载前及下载过程中检查，不能仅收尾告警或仅按文件预估大小判断。
- [ ] 临时音频、切片和失败残留纳入预算；触顶停止新增媒体，清理可安全移除的临时文件并保留待办。已有文字可继续提炼；会产生新临时媒体的续跑仍须符合容量预算。
- [ ] 将视频清理改为每日批次收尾统一执行，不逐条立即删除，也不保留 7 天。条件为 ASR 全部分段完成、文字稿已保存且非空、转写成功状态已持久化；不要求笔记生成成功。
- [ ] 清理资格按 ASR 成果判断，不能只限于最终 status 为 transcribed/extracted；后续笔记失败或因缺料标成 skipped 的条目，只要满足 ASR 成功条件也应清理。ASR 失败、零字或文字未落盘的条目保留并计入容量预算。
- [ ] 删除成功后记录 media_deleted；删除失败只重试清理，不回退转写进度。正常完成、额度耗尽或空间触限都进入收尾；意外中断遗留的合格视频在下次启动补清理。触限提前收尾后，余下待办留待次日，不在同日反复开启新批次凑满 50 条。
- [ ] 暂时关闭视频归档、文字备份及外接盘下载路径，关闭挂载探测与相关提示；日常和独立入口遵循同一禁用策略，旧配置仍在或插入外接盘都不能自动恢复交互。功能代码可保留，恢复需明确启用。

ASR 非空但缺少画面信息的条目仍按上述规则删视频，未来 OCR 或重新转写需要重新获取原片，原片失效时可能无法补齐；不为尚未实现的 OCR 额外保留已成功转写的视频。零字视频仍保留，触及容量上限时暂停并提示。
- [ ] 为 ASR、LLM 请求和整轮任务增加有限超时；退出时保存状态并释放锁。验证定时与手动运行不会同时处理同一批任务。

视频“超过 10 分钟跳过”指内容时长；接口等待和整轮执行的超时是另一项运行保护，需要按样本耗时设置。

### 放行标准与后置工作

完成上述代码与隔离验证、本地重置、新基线、新样本正式入库和 launchd 实际触发验收后，可以开启日常定时观察。外接盘交互及其旧数据清理均暂缓，不把盘上旧数据误报为已删除。

当前只需要用户另行决定每天几点执行，并在真实登录过期时配合扫码、验收少量新笔记；无需接入外接盘。其他规则已经确认，无需重复确认数值。

全量历史补录、图集、OCR、固定分类列表、外接盘归档改进和独立入口 `--force` 语义修复可以后置；当前定时不使用全量 init 或 force。原 F3 的待 OCR 占用必须立即计入容量，但其外接归档功能不阻塞本次本地小规模启动。
