# 抖音下载方案对比：dustoff（自研） vs douyin-video（yzfly/douyin-mcp-server）

> 实测日期 2026-08-27，测试视频 `<aweme_id>`（238s，1080p 源）

## 两条取址链路

### A. douyin-video（`~/Documents/.agents/skills/douyin-video/scripts/douyin_downloader.py`）
纯 HTTP，走 **H5 分享页 SSR 数据**：

1. 正则抓分享文本里第一个 URL → `requests.get` 跟随重定向
2. 取最终 URL 最后一段路径当 `video_id`
3. 拼 `https://www.iesdouyin.com/share/video/{video_id}`，用 iPhone UA 请求
4. 正则挖 `window._ROUTER_DATA = (.*?)</script>` → `json.loads`
5. 取 `loaderData["video_(id)/page"].videoInfoRes.item_list[0].video.play_addr.url_list[0]`
6. **`.replace("playwm", "play")`** —— 去水印的关键：H5 接口给的是带水印地址，改一个词换成无水印
7. `requests.get(stream=True)` 分块写盘

### B. dustoff（`~/Documents/dustoff/scripts/get_meta.mjs` + `fetch.mjs`）
起真浏览器，走 **web 正式 API**：

1. 链接归一化 → `https://www.douyin.com/video/<aweme_id>`（支持 `video/` `note/` `aweme_id=` `modal_id=`）
2. `spawn` 系统 headless Chrome（临时 profile）+ `--remote-debugging-port`
3. CDP `Network.enable` → 导航 → 监听 `Network.responseReceived`
4. 命中 `aweme/v1/web/aweme/detail` 时记下 requestId，轮询 `Network.getResponseBody`（最多 18s）
5. 解析 `aweme_detail` → `video.play_addr.url_list`（**整个列表**）+ desc/author/create_time/duration
6. `fetch.mjs` 逐个 `curl -sL --fail`（带 Referer + UA），校验 `size>10KB` 且 `file --mime-type` 是 `video/*`，失败换下一个 CDN
7. 按 `aweme_id` 缓存到 `~/VideoKB/.cache/`，可断点续跑

核心差异：**A 靠猜接口，B 让真浏览器替自己签名**（不碰 `a_bogus`/`msToken` 逆向）。

## 实测结果

| 维度 | A douyin-video | B dustoff |
|---|---|---|
| 取址耗时 | 1.2s | 5.4s |
| 实际清晰度 | **1280×720**，7.53 MB | **1920×1080**，7.90 MB |
| 无水印 | ✅ 抽帧确认 | ✅ 抽帧确认 |
| CDN 备用地址 | 1 个，无 fallback | 3 个，逐个重试 |
| 收藏夹链接 `?modal_id=` | ❌ 解析成 `self`/`discover` | ✅ 显式支持 |
| 下载完整性校验 | 无 | size + MIME 双校验 |
| 缓存/幂等 | 无 | 有 |
| 重依赖 | ffmpeg | Chrome + node≥21 + ffmpeg + whisper |
| 转写 | SiliconFlow SenseVoice 云 API（要 key，要钱，数据出本机） | 本地 whisper（免费、私密、慢） |

清晰度差异根因：H5 接口返回的地址 **URL 里硬编码 `ratio=720p`**，`playwm→play` 只去水印、不提清晰度；web API 的 `play_addr` 给的是 1080p 原档。多出的 2.25 倍像素只多 5% 体积。

## 实测发现的两个问题

1. **A 开箱即挂**：`requests.get()` 是无状态的，抖音在第一次响应里下发的 `ttwid` cookie 被丢弃，服务端因此返回精简页（缺 `videoInfoRes` 一个字段），脚本 `KeyError`。
   - 隔离实验：只带 `ttwid` ✅ / 只带 `__ac_nonce` ❌ / `ttwid` 填垃圾值 ❌ → **唯一关键是服务器真发的 `ttwid`**。
   - `ttwid` 结构 `1|<签名>|<签发unix时间>|<校验串>`，有效期 360 天，是匿名设备标识，不含登录态。
   - **最小修复 = `requests.Session()` + 同一 URL 重试一次**（分享页自己就会下发 ttwid，不必绕首页）。5/5 稳定，平均 0.68s，比首页预热版（0.96s）还快。
2. **B 的 SKILL.md 过时**：`login.mjs`/`get_collection.mjs`（19:07）比 SKILL.md（17:37）新，但 SKILL.md 仍写着「自动读取收藏夹超出本 skill 范围」——Claude 读了不会知道收藏夹功能已经做好了。

## 结论

**下载这一步，B 更好**，且不是小胜：1080p vs 720p、多 CDN fallback、完整性校验、支持收藏夹链接形态。A 唯一优势是快 4 倍、不需要 Chrome。

可借鉴：把 A 的纯 HTTP 路径（补上 cookie 预热）加进 B 当 **fast path** —— 只为转写文字稿时 720p 完全够用，能省掉起 Chrome 的 5s 和内存；要 1080p 存档或 HTTP 路径失败时再回落到 CDP。

## 第二组实测（复现验证）

测试视频：一条约 23 秒、带硬字幕的口播短视频 竖版方屏
输入：`https://v.douyin.com/U94InklYV94/` 短链（A 喂的是完整分享文案）

| 方案 | 成功? | 耗时 | 产物 |
|---|---|---|---|
| A 原版（未修改） | ❌ `错误: 'videoInfoRes'` | 0.92s | 0 字节 |
| A + cookie 补丁 | ✅ | 2.48s | 720×720，1.96 MB，684 kbps |
| B dustoff | ✅ | 6.74s（取址 6.30 + 下载 0.37） | 1080×1080，2.39 MB，836 kbps |

- 两边帧数完全一致（687 帧），确认是同一条片源的不同转码档。
- A 的地址再次是 `...&ratio=720p&line=0` 硬编码 —— 两个样本复现，不是偶然。
- B 拿到 3 个 CDN 地址，第 0 个即命中，下载仅 0.37s。
- 两边均无水印（抽帧确认）。
- B 的 6.3s 几乎全是 Chrome 冷启动 + CDP 握手；真正下载只占 0.37s。
