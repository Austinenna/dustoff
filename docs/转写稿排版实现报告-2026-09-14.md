## 怎么让模型返回 JSON

当前依旧调用项目配置的智谱 `glm-5.3-flash`，请求中设置：

```json
{
  "response_format": { "type": "json_object" },
  "max_tokens": 8000,
  "reasoning_effort": "high"
}
```

系统消息先明确“同时返回分段编号和笔记”，再给出 JSON 样式及每个字段的含义；用户消息提供 `{id, text}` 原稿片段数组。模型返回的 `message.content` 仍是字符串，代码用 `JSON.parse` 解析，再检查核心业务字段的类型与取值。当前没有使用服务端严格 `json_schema`，不能把 JSON 模式说成必需字段一定齐全。

这次成功的真实分段字段为：

```json
{
  "转写排版": {
    "paragraph_starts": ["s005", "s007", "s011", "s015", "s020", "s022"]
  }
}
```

原稿共 25 个片段，第一段默认存在，6 个新段落起点形成 7 段。模型的「正文」仍是提炼笔记，不能充当完整转写稿。

## 保证原稿不变的机制

1. 原始文件按字节读取，严格解码 UTF-8，并验证能够还原。原文字符串及片段索引保持不可变；门槛判断中使用 trim 不会影响快照。
2. 模型只能指定已有片段编号，不能通过接口要求删改、替换、重排或提供转写正文。程序始终遍历整个原稿，分段指令不决定内容是否输出。
3. 排版字段只允许 `paragraph_starts` 数组，编号必须存在、唯一、按原顺序。字段缺失、非法或含其他指令时回退完整原稿，原因进入日志、文档隐藏记录和运行摘要。
4. 使用普通 Markdown 段落，对原始 ASCII 标点做可逆反斜线转义，使 Markdown／HTML 符号作为文字保留；原有换行和空格不清洗，仅在指定位置插入分段空行。不在正文中放 HTML 标签、注释或校验数据。
5. 程序目录 `~/.dustoff/transcript-meta/` 中的 JSON 保存原稿与排版正文的字节校验信息、各段编码长度和格式版本，笔记目录只生成 Markdown。实际临时文件写入并同步后重新读取，根据这些记录仅撤销程序添加的分隔符和转义，逐字节比较原始 TXT，同时再次检查源 TXT 未被修改。全部通过后才重命名替换笔记。配套记录先保留当前旧版和待保存新版，再替换 Markdown；失败时旧笔记仍有校验记录，每次只保留这两个版本。
