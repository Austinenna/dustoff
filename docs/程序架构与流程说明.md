# dustoff 程序架构与流程说明

配套图解：[离线 HTML 架构图](dustoff-architecture.html)。在浏览器中打开，按左侧目录阅读，可切换时序图；无需联网加载图形库。

本文依据 2026-09-12 复核时的代码 `8ceb352`。描述已实现的行为，问题标为 F1–F6，建议不等同于现有功能。运行数据与磁盘容量是当日快照。更完整的复现记录见[项目梳理报告](项目梳理-2026-09-10.md)。

## 2026-09-14 实现更新

当前实际流程：首次自动只建 100 条基线；之后按可靠重叠扫描新增并入持久队列，每天最多 50 个不同条目。媒体写入受 1 GiB 总量和 10 GiB 最低剩余空间保护；ASR 成功且文字可靠非空的视频在批次结束删除。所有外接盘交互暂停，独立入口共用额度与锁。

本地基线、待办与额度仍使用 SQLite。新增 `daily.mjs` 管理日常状态，`incremental.mjs` 管理页链和边界，`policy.mjs` 管理路径、容量、流式写入和超时。`sync.mjs` 复用日常入口的只下载模式，旧全量及 Whisper 单条入口暂停。

真实验证和当前可用命令见[代码改造报告](代码改造报告-2026-09-14.md)。以下章节为 9 月 12 日的完整架构快照，其中外接归档、7 天保留和固定扫描行为已被上述新规则替代。

## 1. 整体目标：把收藏视频变成可回溯的笔记

输入是抖音收藏列表，输出是供 Obsidian 使用的 Markdown 笔记。中间保留视频、纯文字转写稿，以及模型提供时才有的逐词时间戳。

```text
抖音收藏 → ① 采集与下载 → 视频 → ② 转写 → 文字 → ③ 提炼 → 笔记
                  └──────────── SQLite 账本 ────────────┘
```

三段之间用账本保存身份、状态、产物路径和失败次数；不靠“文件在不在”判断完整处理进度。正常链路中，一个视频对应一份转写稿、一篇笔记。缺料时可以暂不生成笔记。

当前仅实现抖音。图集识别后跳过；OCR 只有待补料标记，尚无实际识别流程。跨视频去重、合并、知识图谱与自动定时也不属于现有完整能力。

## 2. 三个阶段，四个入口

| 入口 | 负责什么 | 读取的待办 | 完成后的状态 |
|---|---|---|---|
| `sync.mjs` | 扫描收藏、筛选、下载、写账本 | 本轮扫描中的 pending | downloaded 或 skipped |
| `extract.mjs` | 媒体维护与 ASR 转写 | downloaded | transcribed |
| `notes.mjs` | 把文字整理为笔记 | transcribed | extracted 或 skipped / need_ocr |
| `run.mjs` | 日常逐条串行编排 | 默认取扫描中的 pending；`--no-scan` 取已有 downloaded/transcribed | 逐步推进至笔记或分支状态 |

`run.mjs` 是编排入口，不是第四个处理阶段。它调用下载脚本，import 并复用 `transcribeOne()`、`noteOne()`、`writeNote()` 等函数。被 import 的入口用 `IS_MAIN` 防止自动执行自己的主流程。

### 日常增量：一条处理完，再处理下一条

1. 加载配置，检查提炼 Key（未跳过提炼时），取得 run、collect、extract、notes 四把锁。
2. 检查媒体目录可写并显示空间。
3. 默认扫描收藏夹，导入账本；仅真正扫到底时才尝试取消收藏对账。
4. 挑选待办并应用 `--limit`。
5. 对每条依次下载、转写、提炼，每步完成就写账本，然后处理下一条。
6. 整批结束后归档媒体、备份文字、清理符合保留期的本地视频。
7. 汇总结果、清理旧运行记录、通知、退出并释放锁。

**F1：默认待办集合只包含 pending。** 虽然单条流程能从 downloaded/transcribed 接着走，但默认扫描分支没有把这些积压送进去。当前需显式 `--no-scan` 或分阶段执行来处理积压，不能宣称普通 `run.mjs` 已完整实现自动断点续跑。

`--skip-notes` 到转写为止；`--no-scan` 不处理 pending，因为账本不保存可长期使用的播放地址。`--limit` 限制本轮候选条目数，不等同于媒体总容量限制。

### 存量补录：先批量下载，再处理已有素材

三个独立入口通过账本衔接，各自内部有工作队列；采集下载默认并发 3，ASR 和提炼默认并发 2。三个阶段有各自的锁，代码允许阶段重叠；首次验收可按顺序执行，便于核对。

采用这种方式，是为了在扫描得到的签名播放地址过期前完成下载。地址过期后应重新扫描获取，不能把旧扫描文件当永久下载清单。

**F5：本机初始化落点目前与文档承诺不同。** `DUST_MEDIA_INIT` 未配置，`DUST_MEDIA=~/.dustoff/media` 覆盖了外接盘默认值。直接 `sync.mjs --init` 实际仍落内置盘。应修复选择逻辑或显式配置初始化路径后再做全量。

### 笔记重生成：只使用文字，不再转写

- `notes.mjs --out <目录>`：写试跑文件，不改条目账本，不使用正式运行记录/阶段锁。
- `notes.mjs --stale`：从已正式入库的 extracted 中，选提示词指纹不同的条目，重新调用 LLM、更新原笔记与账本。
- `notes.mjs --force`：批量选择 extracted 重新提炼；它与 extract 的同名参数不是同一种业务操作。
- 默认沿用已有笔记文件名；`--rename` 允许生成新名称，但代码没有自动删除旧文件的步骤。

试跑没有把 `prompt_hash` 写到账本，因此不能靠 `--stale` 找到此前试跑成品。当前正式 extracted 为 0，提示词调试仍需用 `--out`。

## 3. 第一段：扫描与下载

### 登录与扫描

`scripts/login.mjs` 打开有界面的 Chrome，扫码后把登录态留在专用 profile。`get_collection.mjs` 复用 profile，通过 CDP 打开收藏页、滚动触发分页、读取 `listcollection` 响应。

扫描器提取视频 ID、标题、作者、发布时间、时长、图集类型和播放地址；利用每页 cursor 估计收藏时间。页内插值是估计，不保证每条精确时刻。现在尚未实现“遇到已知收藏就停止”，仍受固定数量、翻页停滞和到底信号控制。

扫描时检查登录 cookie，并由 `session_guard.mjs` 写检查记录、登录预警或 `NEEDS_LOGIN`。检测不到登录态会以退出码 4 结束。历史到期记录不代表平台当前一定接受该登录态。

### 先记账，再筛下载清单

```text
扫描 → coll.json → importScan → pendingAmong → todo.json → 下载器
```

`importScan()` 新增 pending；已有条目刷新部分元数据，不覆盖处理状态。`collected_at` 只补空值。`pendingAmong()` 只选 pending，防止已经转写、正常清理掉视频的条目每天重新下载。

下载器识别并跳过图集、超时长和无地址条目；过期地址保持可再处理，不直接变为终态。默认时长上限为 10 分钟。

它优先选低码率且带音轨的档位，尝试多个 CDN 地址，检查大小、视频 MIME 和音轨。所选档位没有音轨时，可回落到 `play_addr`。已有足够大小的缓存文件走缓存分支并探测音轨；这不是完整的全文件校验或 HTTP 字节断点续传。

`sync.mjs` 在下载器完成后批量导入结果；`run.mjs` 每次只喂一条，单条完成就导入。不能把 sync 描述为每完成一个网络下载就即时写库。

### 取消收藏对账

仅全量扫描才调用 reconcile；默认一轮拟标 removed 超过现有活跃条目的 10% 时拒绝。removed 是账本状态，本操作不会顺便删除视频或笔记。重新扫描到 removed 条目也不会自动恢复为 pending。

## 4. 第二段：媒体维护与 ASR

独立 `extract.mjs` 的执行次序是：

```text
归档历史媒体 → 备份已有文字 → 清理过期本地媒体
    → 查询待转写 → 检查临时空间 → 并发转写 → 备份新增文字 → 运行汇总
```

归档在转写前执行，所以本轮新转写的视频通常在下一轮 extract 开头归档；run 则在当轮整批处理结束后归档。这两种编排的维护时点不同。

单条转写步骤：

1. 从账本取得媒体路径，确认文件存在且有音轨。
2. ffmpeg 剥成 16 kHz、单声道、32 kbps MP3，放系统临时目录。
3. 用 ffprobe 读时长；超过 290 秒则按静音位置规划切片。
4. 将音频以内联 base64 发送云端 ASR；默认模型为代码配置的 `qwen-audio-3.0-asr-flash`，支持领域热词。
5. 合并文字；存在逐词时间戳时，加回各片的时间偏移。
6. 写 `<id>.txt` 及可选 `<id>.words.json`，记 transcribed，清理该条临时音频。

0 字仍属于一次有效转写结果；提炼阶段再判断是否需要 OCR。独立 extract 会在临时盘不足 1 GiB 时拒绝转写，但这不是整个程序的下载容量保护；run 复用的是单条函数，并不执行独立 main 的全部前置检查。

**F4：`extract.mjs --force` 实际批量选择 transcribed 重转，不是文档所说的 failed 重试。** 不能用它作为通用故障恢复命令。

## 5. 第三段：笔记提炼

读取纯文字稿后，少于配置阈值（默认 50 字）直接进入 `skipped / need_ocr`，不调用模型。其余内容调用 LLM，默认模型为代码配置的 `glm-5.3-flash`，输出约定 JSON。

模型可判“够写”或“不够写”。不够写则进入待 OCR；够写时正文不得为空，随后生成 Markdown。内容足够成稿但部分信息缺失的，可入库为 extracted 同时保留 `needs_ocr=1`。

笔记含标题、来源、作者、视频 ID、链接、发布/收藏/提炼日期、时长、转写稿路径、分类、时效与标签。正文去重复口语，尾部附缺料或引流说明与来源链接。

收藏日期优先用 `collected_at`，没有则回退到 `first_seen`。文件名由日期和主题构成，已有正式文件默认保持名称。提示词的 SHA-256 前 8 位作为 `prompt_hash` 写入账本，供以后选择过期笔记。

现有历史试跑发现短稿容易扩写，笔记质量仍待验收；“JSON 合法、正文不空”只是程序校验，不能替代内容质量检查。

## 6. 状态、失败与恢复

| 状态 | 含义 | 正常后继或恢复方式 |
|---|---|---|
| pending | 已知条目，等待下载 | downloaded / skipped；扫描提供新鲜地址 |
| downloaded | 媒体已记账，等待 ASR | transcribed；由 extract 或 run 的积压模式处理 |
| transcribed | 文字已记账，等待提炼 | extracted / skipped；由 notes 处理 |
| extracted | 笔记已正式入库 | 可按提示词版本重新提炼 |
| skipped | 图集、过长、无地址或材料不足 | 需有针对性地重新排队；OCR 回流尚未实现 |
| failed | 失败次数达到上限或判永久错误 | 人工定位失败原因和所处阶段 |
| removed | 全量对账确认本轮收藏列表中不存在 | 不自动删除已有产物，也不自动恢复处理 |

一般异常在未超过上限时保留原处理状态、增加 attempts；默认上限 3。部分永久错误一次就判 failed。ASR/LLM 请求本身还有最多 3 次带退避重试，所以一次条目失败不等同于一次网络请求。

**F2：run 下载失败会在 `importDownload` 和 `markFailed` 各记一次 attempts。** 默认上限下，两轮下载失败可能就被放弃。独立 sync 的下载失败只累加次数，没有同样调用 `markFailed` 的上限终结流程；不能把三段的失败控制说成完全统一。

run 默认连续 3 条链路失败中止。独立 extract/notes 也有连续失败阈值，但并发中可能已有请求在途。中止与零散失败的退出行为不同。

`ledger requeue` 当前统一退回 pending、清零失败计数，不能自动根据已有文件恢复到最省成本的阶段。OCR 补料完成后退回 transcribed 是后续设计，不是已具备的 CLI 操作。

### 公共运行骨架

`stage.mjs` 提供 PID 锁、过期锁接管、日志、运行记录、通知和退出清理。各独立阶段锁不同；run 同时取得自己的锁和三段锁。SQLite 开 WAL、设置 busy timeout，支持阶段读写；阶段互斥与避免重复处理仍依赖程序锁，不能由 WAL 单独保证。

运行记录通常在 `~/.dustoff/runs/<时间戳>-<阶段>/`，保留期限默认 30 天。预览和试跑是特殊模式，并非所有入口都具有相同的无写入行为；例如部分预览仍会创建目录或打开账本，不应将 `--dry-run` 理解为严格只读。

| 退出码 | 含义 |
|---|---|
| 0 | 正常结束，可能包含未触发中止阈值的单条失败 |
| 1 | 执行错误或失败触发中止 |
| 3 | 同阶段已有实例 |
| 4 | 采集检测到登录失效 |
| 5 | 显式检测到磁盘或目标路径不可用 |
| 6 | 缺必要配置或配置校验失败 |

## 7. 文件存储与小磁盘边界

| 数据 | 位置 / 配置 | 写入与用途 |
|---|---|---|
| 代码与文档 | 项目目录 | Git 管理，不存实际视频 |
| 配置、profile、会话记录 | `~/.dustoff` 下 | 含私密凭证，不随架构资料分发 |
| SQLite 账本 | 默认 `~/.dustoff/index.sqlite` | 各入口的共享状态；目前没有自动账本备份 |
| 工作视频 | `DUST_MEDIA` | 下载产物与元数据，供 ASR 消费 |
| 临时音频 | 系统临时目录 | 转写中产生，正常完成后清理 |
| 转写稿与逐词数据 | `DUST_TEXT` | 本机保留，供反复提炼与时间线查看 |
| 媒体归档 | `DUST_MEDIA_ARCHIVE` 或外接根目录下 `dustoff-media` | 复制目录、核对文件数及字节数、删除源目录、更新账本路径 |
| 文字备份 | `DUST_TEXT_BACKUP` 或外接根目录下 `dustoff-text` | 复制，本地保留；不随源删除，按大小跳过或覆盖，不是历史版本库 |
| 最终笔记 | `DUST_NOTES` | Obsidian 使用；本机当前为 iCloud vault 内目录 |

归档前检查目标是否处于不同设备；并非仅看目录存在。复制核对不是内容哈希校验。归档复制成功后的删除与账本更新分开执行，不能称为跨文件系统与数据库的原子事务。

清理仅选位于工作媒体路径下、状态为 transcribed/extracted、过保留期且未标删除的条目，再检查文字文件存在且记录字数非零，删除视频目录并更新 `media_deleted`。默认期限从 `transcribed_at` 起算 7 天，与笔记是否生成无关。归档路径在工作目录之外时不受此清理范围约束。

**F3：待 OCR 的 skipped 条目既不进入当前媒体归档查询，也不进入过期清理查询。** 因此可能长期滞留本地；转写失败或尚未转写的视频也不受“7 天清理”统一管理。

**F6：5 GiB 空间阈值仅在 sync/run 收尾告警，下载没有空间硬停止或缓存容量上限。** run 还在整批后才归档。外接盘不在时跳过归档，但仍可能继续处理并清理到期媒体。

适合小磁盘的下一步策略是：全量直写确认挂载的外接盘；内置盘只留小缓存和文字；下载前及过程中检查空间；本地缓存达到上限或外接盘未挂载时暂停新增媒体。建议初始保留 15 GiB 空闲、缓存约 2 GiB，但这尚未实现，也不是当前配置能直接保证的能力。

## 9. 当前放行判断

截至 2026-09-12：48 条账本中有 27 条待转写、12 条已转写、9 条图集跳过，没有正式入库笔记；内置盘剩余约 29 GiB、工作媒体约 138 MiB，T7 未挂载。

可以先用现有文字试跑笔记，不需要先下载全部收藏。全量前先处理 F5、F6 并核实外接盘；无人值守前修复 F1–F4、验收笔记、确认备份及失败通知。然后人工监督跑 5–10 条，验证入库、归档、重复运行与空间不足时的行为，再逐步扩大。

本套资料只讲解程序；HTML 内没有真实启动、下载、清理或调用模型的按钮。查看图解不会运行项目，也不会上传本机资料。
