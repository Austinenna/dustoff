# dustoff 架构变更记录

> [`架构.md`](架构.md) 是当前状态的快照，不含历史。本文记录**架构改过什么**：
> 从什么改到什么、什么时候改的、为什么改。
>
> 只记录**架构层面的决策**——影响系统怎么切分、数据怎么流动、依赖什么外部服务的改动。
> 单纯的 bug 修复不进这里，除非它推翻了某个设计假设。
>
> 倒序排列，最新在上。

---

## 2026-09-02

### 澄清：`sync.mjs` 不调用 `extract.mjs`

**改动**　第一段的入口只管采集，不串第二段。README 里「唯一入口」的说法一并改掉。

**为什么记这一条**　这不是新决策，而是**纠正一次自己的跑偏**。
架构从一开始就写着两段分离、各有定时器，但在讨论「怎么手动跑通全链路」时，
我把两件事混为一谈了：

```
需求      能用手动的方式跑通全链路
误解成    把全链路塞进一个进程
```

合并会具体损失什么：登录态失效时 `sync.mjs` 在第一步就 `die(4)` 退出，
永远走不到提取——而账本里可能还躺着几十条已下载待转写的，
它们完全不受登录影响。这正是当初写「采集挂了不该影响提取（还有积压可做）」
要防的那件事。

而且合并会让账本的角色被架空：账本存在的意义就是当两段之间唯一的接口，
再加一条直接调用就成了双重耦合。

**正确形态**　手动跑全链路 = 依次跑两条命令；以后两个定时器跑的是同样这两条。
手动与自动之间不改任何代码——这才是「分离 ≠ 手动」的真正含义。

### `reconcile()` 加两道硬闸

**改动**　从「可以裸调」变成「必须显式声明全量扫描，且删除比例超阈值就拒绝」。

**为什么**　这是全项目最危险的一个函数——它按「不在名单里」判死，
而名单是外部给的。原先只有一行注释说「必须全量扫描后才能跑」，
**注释拦不住调用**。日常扫描只覆盖最新 200 条，拿它对账会把其余五千多条
全部误标为已取消收藏。

第二道闸（删除比例 > 10% 就拒绝）防的是另一种情况：**自称全量、其实扫挂了**。
早期滚动容器找错导致扫描只返回 69 条却一切正常地退出，正是这种。
没有这道闸，一次静默的扫描故障就会毁掉整本账。

---

### 第一段接上账本

**改动**　`sync.mjs` 扫描后调 `importScan`、下载后调 `importDownload`，
全量扫描时额外 `reconcile`；跑完提示第二段的积压量。

**为什么**　账本此前只有 `extract.mjs` 一个使用者，导入全靠手动敲 CLI。
第一段不写账本，两段之间就没有共享状态，「分离但通过账本对话」这个设计
只存在于文档里。

### 修一个潜伏的 stdout 截断 bug

**改动**　`get_collection.mjs` / `get_meta.mjs` 输出 JSON 后不再立刻
`process.exit()`，改为等写入回调触发再退出。

**为什么记进架构变更**　它推翻了一个隐含假设：**「子进程的输出总是完整的」**。

```js
console.log(JSON.stringify(bigObject));
process.exit(0);                          // ← stdout 是管道时，没写完的部分直接丢弃
```

stdout 是管道时写入是异步的，超过缓冲区（macOS 64 KB）的部分排队等待，
而 `process.exit()` 立刻终止进程。结果是一个**正好 65536 字节、被腰斩的 JSON**。

这个坑潜伏了很久，因为它只在被父进程用管道接收时才出现——直接跑到终端（TTY）
或 shell 重定向到文件都是同步写，看不出问题。所以它一直等到
`sync.mjs` 第一次接管扫描输出才暴露。

**如果没在这时候撞上**，`node sync.mjs --init` 扫 5831 条时 coll.json 会在
64 KB 处被腰斩，下游要么解析失败、要么只处理其中一小部分。

### mp4 清理策略定案

**决定**　转写完成后**保留 7 天再删**；删之前**不存关键帧**。
连带**废掉「只有到 `extracted` 才可删」这条旧规则**。

**为什么废掉 `extracted` 闸门**　它的唯一理由是 OCR 增强要靠 mp4 抽帧，
而关键帧方案在同一次决定里被否了——理由没了，规则不该留着。何况第三段
消费的是 `.txt`，根本不碰 mp4；绑着它只会让第二段的磁盘占用被第三段的进度
绑架：第三段一天不开工，`extracted` 就一天到不了，等于一个 mp4 都删不掉。

**为什么留 7 天**　转写质量目前只在少量样本上验证过，热词表也还在长。
删早了发现问题就得重新下载，而 CDN 地址会过期，等于要重新扫描一遍。

**为什么不存关键帧**　存 12 张（约 1 MB/条，全量约 4.7 GB）本意是给未来的
OCR 增强留原料，但实测关键帧对屏幕录制会漏 73%——**这个保险不保靠**，
不值得为它长期占 4.7 GB。将来真做 OCR 时按需重下。

### 笔记提炼移到第三阶段

**改动**　第二段的出口收缩为「语音转文字的 `.txt`」，到此为止。
笔记提炼、分类、时效判断全部归第三阶段。

**为什么**　原先第二段的终点是「笔记已生成」，而笔记格式和 prompt 都还没定稿，
导致第二段没有一个可验证的终点。收缩之后第二段有了干净的完成标准，
可以先打通、先自动化，不必等 AI 那部分想清楚。

**连带影响**　`cleanable()` 查的是 `status='extracted'`，
但新分段下第二段的终态是 `transcribed`——不改就永远找不到可删的。
这一条尚未实现，记在待办里。

### 转写模型：`qwen3-asr-flash` → `qwen-audio-3.0-asr-flash`

**改动**　默认模型换代，并新增 `DIALECTS` 适配层，让模型成为配置项而非硬编码。

**为什么**　发现同一个同步端点上还有更新的一族。两者**同价**
（¥0.00022/秒，已核实官方定价页），但 `qwen-audio-3.0` 多三样：
逐词时间戳（笔记能标「这句在第几秒」）、更新的一代（2026-07 发布
vs 2025-09）、36,000 秒免费额度。

**代价**　两族的请求与返回形状完全不同：

| | qwen-audio-3.0 | qwen3-asr |
|---|---|---|
| 额外请求参数 | `parameters.format` 必传 | 无 |
| 取文本 | `output.text` | `output.choices[0].message.content[0].text` |
| 计费秒数 | `usage.duration` | `usage.seconds` |

隔进 `DIALECTS` 之后换模型只改 `DUST_ASR_MODEL`。这个抽象的动机来自
paraformer 那次教训——**模型会过时**，下次再出新的不该动业务代码。

**提交**　`1e9839b`

### 无人声视频：失败 → 有效结论

**改动**　ASR 返回「没识别到任何词」时，记为「0 字」正常收尾，不再算失败。

**为什么**　两族模型对此的表现不一样：`qwen3-asr` 返回 200 + 空文本，
`qwen-audio-3.0` 却报 400 `ASR_RESPONSE_HAVE_NO_WORDS`。换默认模型后
第一条验证就撞上了。

按失败处理有三个后果：白重试三次、状态错标成 `failed`，而且
**这类「纯画面无人声」的条目正是 OCR 增强要挑的目标**，
标成 `failed` 就永远进不了候选名单。

这不只是 bug —— 它暴露了一个设计假设的漏洞：**「没有输出」不等于「失败」**。

**提交**　`1e9839b`

### 端点选择定案：留在同步，接受切片

**改动**　确认不迁移到异步端点（`fun-asr`、`*-filetrans`），保留 290 秒切片逻辑。

**为什么**　异步端点不限音频时长，看起来能省掉切片代码。但故障面差距悬殊：

```
同步   请求 → 结果                                     1 处会挂
异步   换凭证 → 传 OSS → 提交 → 轮询 → 取结果 URL → 下载   8 处会挂
```

这段代码跑在**凌晨 3:30 无人值守**——多出来的分支平时不执行，
只在半夜出问题时第一次被真正跑到。异步还有个悬而未决的问题：轮询多久算超时。

切片的代价则小得多：超 290 秒的只占 9%，日常摊下来每天约 1.1 条，
且是纯本地确定性操作，接缝按静音中点下刀实测不劈词。

**翻转条件**　如果把 10 分钟的下载上限大幅放宽（比如到 60 分钟），
每条就是 13 次请求、13 个独立失败点，届时异步的单任务更稳。

### 状态机：6 态 → 7 态，新增 `transcribed`

**改动**　`downloaded → extracted` 之间插入 `transcribed`。

**为什么**　转写（ASR，机器干的）和提炼（LLM 写笔记，prompt 说了算）
是性质不同的两件事：失败原因不同、重跑代价也不同。合成一个状态的话，
**笔记模板一改就得连 ASR 一起重跑**，等于为改 prompt 重复付一次转写的钱。

另一个后果更严重：`cleanable()` 认的是 `extracted`。只做完 ASR 就标
`extracted`，会让清理逻辑在笔记还没写的时候就把 mp4 删掉——
而 OCR 增强还要靠它抽帧。

**顺带**　账本加了 `migrate()`。早期改字段靠删库重建，40 条时无所谓，
但全量 5831 条之后重扫一次要十几分钟，不能再那么干。

**提交**　`d8ffec8`

## 2026-09-01

### 提取路径：抽帧 + 本地 OCR + 多模态 → 纯云端 ASR

**这是本项目至今最大的架构改动。**

**原方案**

```
密集抽帧（约 210 帧/条）──→ 本地 Vision OCR ──→ 字幕文本 ─┐
                                                        ├─→ 一次多模态调用 ─→ 笔记
关键帧 12 张（场景切变 + 感知哈希去重）───────────────────┘
```

**现方案**

```
剥音轨 ──→ 云端 ASR ──→ 转写稿 ──→（提炼笔记，尚未实现）
```

**为什么**

原方案的核心假设是「**硬字幕是内容的主要载体，本地 OCR 读它就够**」。
这个假设有一半是错的：

1. **本地 OCR 读的是字幕，而字幕只占屏幕文字的一小部分。**
   实测逐帧 OCR 出的 467 个片段里，只有 35 个是字幕。
2. **关键帧漏得厉害。** 屏幕录制是连续滚动的，场景检测抓不住渐变，实测漏 73%。
3. **密度差 130 倍。** 纯口播那条逐帧跑 13.6 秒只换来 105 字，
   而屏幕录制那条有 13890 字。一刀切的抽帧策略两头不讨好。

同时用户明确要求「**先只用 ASR 来简单一点**」。

**OCR 没有被否定，而是被重新定位**：它的职责从「捞硬字幕（必需路径）」
变成「捞屏幕文字（可选增强）」。ASR 已经覆盖了口播内容，OCR 要解决的是
ASR 天生拿不到的那部分——实测一条屏幕录制视频 ASR 171 字 vs OCR 9396 字。
依据与实现方案完整保留在 [`待办-OCR增强.md`](待办-OCR增强.md)。

**提交**　`d8ffec8`

### whisper：兜底 → 淘汰

**改动**　不保留本地 whisper 作为任何形式的兜底。

**为什么**　同一条视频、真值取自画面硬字幕，8 个技术专名：

```
云端 ASR       错 1/8   （只有 HTML→HPM）
whisper base   错 8/8   （Claude Code→Cloud Code、时序图→实序图、重绘→重惠…）
```

差距太大，而云端一条 3.5 分钟的视频只要 ¥0.046。留着它当兜底
只会在云端出问题时**悄悄产出一批不能用的笔记**，比直接失败更糟。

### ASR 模型初选：`paraformer-v2` → `qwen3-asr-flash`

**改动**　换掉最初选的模型。

**为什么**　`paraformer-v2` 是**照抄 TokBrain 的配置定的，没有评估过**。
查官方文档发现 Paraformer 是上一代，明确建议迁移。后来实测也印证了——
同一条射频课，`paraformer-v2` 把「图传」认成「图层」、「设计动机」认成
「射计动机」、「公式」认成「工序」（5 次）。

**教训**　抄别人的配置时要连「为什么这么选」一起抄，抄不到就自己评估。

**提交**　`63a244d`

### 下载挑档：最低码率 → 最低且带音轨

**改动**　`pickLowestGear` → `pickGear({ requireAudio })`，并加 ffprobe 校验闸门
与 `play_addr` 回落。

**为什么**　这是个**由架构变更引发的连锁问题**。原先的假设是
「只要内容不要原件，所以取码率最低档」——这在提取靠 OCR 时成立（不需要声音）。
改成 ASR 之后音轨变成必需品，而实测 **58% 的视频最低那几档是纯视频流**。

存量里已有 18 条是哑的，等于白下。

**代价**　体积只涨 18%（多的是一条 55 kbps 音轨，不是跳到 `play_addr` 的 2.5-3.3 倍）。

**教训**　「不要原件只要内容」这个前提没变，但「内容」的载体从画面变成了声音。
**前提没变不代表推论没变。**

**提交**　`63a244d`

### 成本模型修正

| | 原估算 | 现（已核实） |
|---|---|---|
| 单条 | 约 ¥0.042 | 均值 104 秒 ≈ ¥0.023 |
| 日常增量 | 约 ¥13/月 | **¥8.4/月** |
| 存量全量 | 未估 | **约 ¥109** |

**为什么**　原估算基于「密集抽帧 + 多模态调用」，改成纯 ASR 后便宜得多。
单价 ¥0.00022/秒先从账单反推（1783 秒 → ¥0.39226，500 秒 → ¥0.11，
两次都严丝合缝），后经官方模型详情页核实一致。

### 状态载体：文件系统 → SQLite 账本

**改动**　新增 `scripts/ledger.mjs`。

**为什么**　v0.1.0 的「状态」全靠文件系统——「media 目录里有没有这个文件夹」
就是全部。这够用到下载为止，但撑不到提取阶段，因为下面这些问题文件系统答不了：

- 哪些下好了但还没提取？
- 哪些提取失败了、失败几次了、还该不该重试？
- 哪些提取完了、mp4 可以删了？（**按状态删而不是按时间删**）
- 哪些是主动跳过的（图集 / 超长）？
- 哪些已经从收藏夹里被移除了？

**为什么是 SQLite 而不是 JSON**　五千条量级下 JSON 每次都要全量读写；
而这里最频繁的操作是「按状态查一批」，正是索引擅长的事。
另外两个定时任务可能重叠，SQLite 的事务比手工读写 JSON 安全。
用 Node 22 内置的 `node:sqlite`，零依赖。

**提交**　`8325c1f`

## 2026-08-31

### 项目形态：Skill → 独立脚本 + 单一入口

**改动**　不做成 Claude Code Skill，改为普通 Node 脚本 + `sync.mjs` 统一入口。

**为什么**　Skill 的触发方式是「对话里提到就加载」，而这个系统的目标是
**每天凌晨无人值守自动跑**。定时任务不需要一个会话来承载它，
跑 launchd 调用一个脚本就够了。

单一入口的作用是把六个脚本的调用顺序、配置传递、失败处理收在一处，
让 launchd 那一行只需要写 `node sync.mjs`。

### 项目改名：`douyin-kb` → `dustoff`

**改动**　目录、变量、路径全部改名，迁到 `~/Documents/dustoff/`，初始化 git。

**为什么**　后续要扩展到其他平台，名字里带 `douyin` 会限制住。
账本的主键也因此定成 `(platform, id)` 联合主键——跨平台时 id 可能撞车。

**提交**　`38d6360`
