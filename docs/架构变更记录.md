## 2026-09-05

### 日常增量改用串行编排：新增 `run.mjs`，三个入口原样保留

**改动**　多一个入口 `run.mjs`：扫一次收藏夹，然后**逐条串行**走完
下载 → 转写 → 提炼。`sync` / `extract` / `notes` 一个字没改，仍各自可单独跑。

```
日常增量   node run.mjs                 一趟串行跑完，约 4 分钟 / 20 条
存量补录   node sync.mjs --init  → …    必须分段，理由见下
改提示词   node notes.mjs --stale       只跑第三段
```

**这不是第二套实现。** `run.mjs` 从 `extract.mjs` / `notes.mjs` import
单条流程（`transcribeOne` / `noteOne` / `writeNote`）和三个收尾动作
（归档 / 备份 / 清理），共用同一本账本、同一套状态机。两个入口加了
`IS_MAIN` 守卫：直接跑时照旧执行 `main()`，被 import 时不自动跑、
也不建自己的运行记录目录。

**为什么日常增量该串行**　按实测算，20 条一天：串行约 4 分钟，
分段并发约 2 分钟。差两分钟，发生在凌晨没人等的时候。而串行白送四样：

| | |
|---|---|
| 限流不用管 | 并发 1 = 最多 1 QPS。三个并发上限（CDN 3 / ASR 2 / LLM 2）**至今没人实测过**，配置注释里写的是「没测过，从 3 起步比较稳」——串行就不需要知道 |
| `spawnSync` 不再是问题 | ffmpeg 走的是同步调用，会阻塞事件循环（实测剥音轨 0.27 秒）。并发 1 时没有别的东西在等，缺陷退化成实现细节 |
| 止损闸变精确 | 并发跑时数到第 3 个失败，前面若干条其实已经发出去了；串行下「连续 3 条」是真的连续 |
| 日志是线性叙事 | 一条视频、三步、按顺序。凌晨出问题时不用在交错的日志里拼时序 |

**为什么存量补录不能用它**　CDN 签名地址有效期 3~24 小时，而
5831 条 × 约 24 秒 = **39 小时**，跑到一半地址全过期。存量必须
「趁地址新鲜批量下完，再慢慢转写提炼」——那正是分段的形状。
**两种编排都要留着，它们服务的是两件不同的事。**

**三把锁全攥住。** `run.mjs` 同时扮演三个阶段，所以要同时持有
`.lock.collect` / `.lock.extract` / `.lock.notes`（外加自己的 `.lock.run`）。
不这么做的话，`run.mjs` 跑着时 `extract.mjs` 照样能起来，两边捞到同一批
`transcribed` 条目，对同一条视频付两次 ASR 的钱——账本的 WAL 保证不写坏，
保证不了不重复花钱。

**`chainOne` 按状态驱动，不是死板的三步。** 已经是 `downloaded` 的跳过下载、
已经是 `transcribed` 的跳过转写。所以昨天断在半路的今天能接着走，
`--no-scan` 也能拿来消化积压。每一步做完**立刻**写账本——
「串行流式」和「分三段」在可恢复性上等价，靠的就是这个。

**`--no-scan` 只捞 `downloaded`/`transcribed`，不捞 `pending`。**
pending 缺的是播放地址，而 CDN 地址不进账本（带签名、几小时就过期），
不重新扫描根本下不了；捞进来只会白撞一轮然后误标成 `skipped_no_url`。

**顺带**　止损闸阈值 5 → 3（`DUST_ASR_MAX_FAILS` / `DUST_LLM_MAX_FAILS`）。
串行让「连续」这个信号变干净了，可以更敏感。

**代价**　多一个入口要维护；两个入口多了 `IS_MAIN` 这层间接。
换来的是日常那条路上不用再想并发和限流。

## 2026-09-04

### 外接盘收敛成一个根路径 `DUST_EXTERNAL`

**改动**　三处外接盘路径各写一遍完整路径 → 只配一个根 `DUST_EXTERNAL=/Volumes/T7`，
子目录名由程序自己定。

```
DUST_EXTERNAL=/Volumes/T7
├ sync.mjs  --init 下载落点   → /Volumes/T7/dustoff-media
├ extract.mjs mp4 归档目的地  → /Volumes/T7/dustoff-media   （同一个目录）
└ extract.mjs 转写稿备份      → /Volumes/T7/dustoff-text
```

**为什么**　换盘（T7 → T8）时三处都要改。漏改一处不会报错——**会一半文件去新盘、
一半去老盘，而老盘没插时那一半安静地跳过**，未必发现得了。

**为什么两个 mp4 的配置项指向同一个目录**　它们是两个程序在两个不同时刻问的
两个不同问题：`sync.mjs` 问「`--init` 时我下载到哪」，`extract.mjs` 问
「转写完我搬到哪」。答案恰好一样，但提问的时机和主体不同，所以是两个键。
两批 mp4 最终躺在同一个目录里也不打架——它们在生命周期上是接续的，
不是并行的，账本里各自 `media_path` 指对即可。

**代价**　三个细分键保留为覆盖项（命令行 > 细分键 > `DUST_EXTERNAL` 推导），
想把转写稿和视频分到两块盘仍然可以。默认不必知道它们存在。

### 转写稿备份到外接盘：**复制**不是移动，只增不删

**改动**　`extract.mjs` 新增 `backupText()`，把 `~/.dustoff/text/*.txt`
复制一份到 `$DUST_EXTERNAL/dustoff-text/`。

**为什么保护力度要跟体积反过来**

| | 一年体积 | 丢了怎么办 |
|---|---|---|
| mp4 | 约 16.5 GB | 重下，免费（作者删号除外） |
| 转写稿 | 约 35 MB | **重转，全量约 ¥109** |

体积差 479 倍，可再生性正好相反。原先的设计只保护了大的那个。

**三条与 mp4 归档不同的地方**

- **复制不是移动**。本地那份必须留着——第三段每次提炼都要读它。
- **只增不删**。本地删掉的，外接盘那份不跟着删；跟着删就不叫备份了。
- **每轮跑两次**：开头一次（把之前欠的补上），转写完再一次（把本轮新产的带上）。

**代价**　同一份数据存两处，要接受它们可能不一致。选择是「外接盘只多不少」——
不一致的方向是确定的，就不算问题。

## 2026-09-03

### 归档改为默认行为，不再是可选加装件

**改动**　mp4 归档从「配了 `--archive-to` 才做」→ **默认就做**，
路径由 `DUST_EXTERNAL` 推导。

**为什么**　默认关闭的备份等于没有备份。原先要每次记得加参数，
而这段代码的目标场景就是无人值守——凌晨定时器不会记得加参数。

**代价**　没插外接盘时每轮多一次挂载点探测（一次 `statSync`，可忽略）。

### 转写完的 mp4 归档到外接盘，每轮全量补课

**改动**　`extract.mjs` 在转写之后、清理之前，把已转写且还在本地的 mp4
**移到**外接盘。不是只处理本轮新转的——**每轮都从账本全量扫一遍**，
把之前因为没插盘而错过的一并搬走。

**为什么要全量补课**　只处理本轮的话，某天没插盘，那批就永远留在本地，
7 天后被保留期删掉。「第二天插上盘，之前欠的一起补」才是完整的语义。
账本里 `status >= transcribed` 且 `media_path` 还在本地前缀下的，就是欠的。

**三道防线**

① **挂载点用设备号判断，不用 `existsSync`。** macOS 上外接盘没挂载时，
`mkdir -p /Volumes/T7/xxx` 会在**启动盘**上真的建出这个目录，程序会兴高采烈地
把 mp4「移到外接盘」，实际全写进内置盘；而 T7 真插上时系统会把它挂到
`/Volumes/T7 1`，文件永远留在那个假目录里。判据改成「这个路径的 `st_dev`
是不是跟 `/` 一样」——一样就说明盘没挂载，直接跳过，**绝不建目录**。

② **先复制、核对、再删源。** 核对的是**整个目录**的文件数与总字节，
不是只看账本记的那个文件名——实测撞到过一条账本记 `video.mp4`、
磁盘上实际叫 ` .mp4`（旧下载器的遗留 bug）。核对不过就保留源文件。

③ **保留期只管本地。** `cleanable()` 加 `underPath` 参数，把清理范围限定在
工作媒体目录内。归档到外接盘的条目路径在这个前缀之外，天然出了保留期的管辖。
**不加这道过滤的话，归档等于白做**——搬过去 7 天后照样被删。
用路径前缀而不是新加一个 `archived` 字段，是因为「文件在哪」本身就已经
回答了「归没归档」，不必存两份真相。

**顺序是关键**　归档必须跑在清理之前。反过来的话，插盘那天正好有条目到了第 7 天，
会被删在搬走之前。

**代价**　exFAT 不支持扩展属性，macOS 会给每个文件写一个 `._` 伴生文件；
目录核对必须跳过 `._*` 和 `.DS_Store`，否则源和目标永远对不上。

### prompt 版本号进账本；豆包 ASR 搁置

**改动**　账本加 `prompt_hash`（提炼指令的 sha256 前 8 位），`notes.mjs` 加 `--stale`。

**为什么**　prompt 会反复改。没有版本号的话，改完只能「全部重跑」或者
「凭记忆挑」。有了它，`--stale` 精确捞出还停在旧版指令的那些。

**只哈希 PROMPT 本身，不把模型和 effort 算进去。** 算进去的话，
做一次 effort 的 A/B 对照就会把全部笔记标成过期——那不是过期，是换了个档跑。

**豆包 ASR 搁置**　`volc.bigasr.auc_turbo` 只有异步端点，要轮询、要回调，
故障面比同步大一截。当前 `qwen-audio-3.0-asr-flash` 够用，配置项留着但不接。

### 三个日期：发布 / 收藏 / 提炼，删掉下载日期

**改动**　笔记 frontmatter 的四个日期砍成三个。删掉的是**下载日期**，
留下的第三个改名叫 `提炼日期`。

**为什么删下载日期**　它跟收藏日期只差 0~1 天（当天扫到当天下），是条冗余信息。

**为什么留的是「提炼日期」而不是「下载日期」**　起初我把「重跑会变」当成缺点，
反了：同一份转写稿会被不同版本的 prompt 反复提炼，**「这篇笔记是什么时候
变成现在这个样子的」才是有效信息**，而下载日期从此不再变化，也就不再有信息量。

叫「提炼」不叫「提取」，是因为「提取」已经是第二段的名字。

### 笔记文件名认第一次，不跟着标题变

**改动**　重新生成笔记时沿用已有的文件名，不跟着新标题走。想改名加 `--rename`。

**为什么**　实测同一条视频两次生成，10 篇里 8 篇标题不一样。文件名跟着标题走的话，
每次重跑都会在知识库里留下一堆孤儿文件，还会打断 Obsidian 的双链。

**名字是身份，内容才是产物。**

### frontmatter 字符串加引号：19 位视频 ID 会被 YAML 读坏

**改动**　frontmatter 里所有字符串值加双引号。日期故意不加。

**为什么这不是洁癖**　抖音的 `aweme_id` 是 19 位数。不加引号的话 YAML 解析器
按整数读，而它超过 JS 的安全整数上限（2^53 ≈ 9.007e15），转成 float64
末几位就丢了：`7676650803859361059` 读成 `7676650803859360768`。
**文件里的字符是对的，读出来的值是错的**——这种坏最难发现。

日期不加引号是为了让 Obsidian 认成日期类型，能排序能筛。

### 笔记带上回源路径

**改动**　frontmatter 加 `转写稿: <绝对路径>`，正文末尾加一行
`[转写稿](file://…) · [原视频](https://…)`。

**为什么两处都要**　frontmatter 那份给程序读（将来批量重跑要靠它定位），
页脚那份给人点（在 Obsidian 里一下就能跳回去）。**笔记是派生物，
改 prompt 随时能重生成；转写稿是花钱买的、不可再生**——回源路径不能只存在于账本里。


### 第三段落地：`notes.mjs`

**改动**　新增第三段入口，跟 `sync.mjs` / `extract.mjs` 平级，同样只通过账本对话。
账本补 `markSkipped()`——第三段判「材料不够」时要用，之前没有这个写入口。

**两个设计选择值得记**

**① 试跑模式 `--out DIR`：写文件但不碰账本。**
prompt 要改很多轮，定稿前生成的笔记不该进知识库、更不该把条目标成 `extracted`——
否则每改一版就要手工清一次现场。有了它，「改 prompt → 重跑 12 条 → 读成品」
这个循环的成本是 ¥0.04 和二十秒。

**② 「材料不够」走 `skipped` 而不是 `failed`。**
那不是失败，是原料缺一块。落 `skip_reason='need_ocr'` + `needs_ocr=1`，
等 OCR 补完画面文字再退回 `transcribed` 重走一遍。
规则里没有「因为题材不高级所以扔掉」这一条——收藏这个动作本身就是信号。

**冒烟测试的两条实物验证了两个之前只是纸面上的判断**

一条 19 秒的数码配件带货视频，模型按「推销物 = 主题」判成正文，写出了一篇正经的产品笔记
（把型号、现价、工艺都提了出来），没有当成引流剔掉——这正是「我就是想收藏一个广告」
那个顾虑的答案。两条的 `needs_ocr` 理由也都具体：一条缺购买链接和配列，
一条缺开源仓库地址，都是确实只在画面上的东西。

**文件名**　优先在标题的第一个冒号处切，比硬截体面：
`某某产品名：169 元的某某卖点描述` → `某某产品名`。
切出来少于 6 字（冒号在开头）才回退到硬截 30 字。

## 2026-09-02

### 第三段选定智谱 GLM-5.3-Flash，继续零依赖

**改动**　配置加 `DUST_LLM_*`（key 在 `~/.dustoff/dustoff.conf`，仓库里只有 example 占位）。

**为什么不装 SDK**　智谱是 **OpenAI 兼容的 Chat Completions**，裸 `fetch` 就能调，
和第二段调 DashScope 的写法一致。装一个 SDK 只为打一个兼容端点不划算，
项目继续保持零 npm 依赖。

**这个模型的性格决定了第三段怎么写**（实测，非文档）：

真稿 1010 字，每档跑 4 次，数字是 `reasoning_tokens`：

```
不传任何 effort                     [ 2281  1121   634   126]   均 1041
reasoning_effort=max               [ 1320  1327  2529   529]   均 1426
reasoning_effort=high              [    7    94     5     5]   均   28
reasoning_effort=low               [    0     0     0     0]   均    0
thinking:{enabled, effort:'low'}   [  325  1510   571  1290]   均  924   ← 参数名错了，被无视
```

**不传 effort 走的是 `max`，不是 `high`。** 配置文件里的 `defaultEffort: high`
描述的是意图，不是接口在参数缺失时的实际行为。

**三档不是均匀的**：`low` 和 `high` 几乎没差别（0 vs 28），`high` 到 `max` 是 ~50 倍的断崖。
`high` 不是中间档，它离 `low` 更近。所以没必要为省钱降到 `low`——
28 个 token 省下来毫无意义，真正要躲的是漏传参数。

| 发现 | 后果 |
|---|---|
| effort 参数名是 `reasoning_effort`，不是 `thinking.effort` | 传错**不报错**，effort 被静默无视，分布和「不传」完全一样 |
| 不传 effort 走的是 `max` | 比 high 贵约 40 倍，且静默——HTTP 200、结果照样对，只有账单变厚 |
| `max` 和「不传」的波动都极大（126~2529） | 单次采样得出的结论不可信，这一节的数字改过两轮 |
| 思考 token 计入 `max_tokens`，且按输出计费 | 首次测试 max_tokens=800，模型思考掉 798，正文空字符串 + HTTP 200 |
| `medium` 是硬错误 | 400，错误码 1210 |

**「强制思考」这个说法要说清楚**：它指的是**不能传 `thinking:{type:'disabled'}` 这个参数**
（传了会被拒），不是指模型一定会思考。`reasoning_effort='low'` 时它是真的不思考——
`reasoning_tokens` 和 `reasoning_content` 两个信号一致，11 次全是 0。
这两件事是不同层面的：一个是 API 参数校验，一个是模型行为。

第三条最危险：**空 content 不报错**。`notes.mjs` 必须把「content 为空」当失败处理，
否则会安静地写出一堆空笔记，还把状态标成 extracted。

`response_format:{type:'json_object'}` 可用，四次测试都能 `JSON.parse`。

### 采集捡回 `cursor`：收藏时刻从「拿不到」变成「拿得到」

**改动**　`get_collection.mjs` 记下每页 listcollection 响应顶层的 `cursor`，
新增 `assignCollectedAt()` 还原每条的收藏时刻；账本加 `collected_at` 列。

**从什么改到什么**

```
之前   账本只有 first_seen（我哪天扫到的），注释写着「≈ 收藏时间」
       实测这个 ≈ 不成立：48 条里 40 条的 first_seen 都是 2026-09-01
       （第一次跑扫描那天），而发布日跨了近两个月。
       存量补录后 5831 条会共用同一天，文件名的日期前缀直接失效。
现在   collected_at 是真收藏时刻的估计值，存量也能还原
```

**怎么发现的**　逐条 aweme 对象里确实没有收藏时间——132 个字段全扫了一遍，
时间戳只有 `create_time`（发布）、`mix_info.*`（合集）、
`play_progress.last_modified_time`（观看进度）。但响应**顶层**的 `cursor`
是微秒级 unix 时间戳，逐页严格递减，就是分页边界的收藏时刻。
采集脚本本来就在解析每一页的响应体，`cursor` 一直在它手里，只是被丢掉了。

**验证**　账本里 `first_seen = 2026-09-02` 的 8 条（前一天扫描之后才真正新增的），
全部落在第 1 页，一条不落；09-01 那批补录的落在 2–5 页；6 页往后是账本从没见过的老条目。

**精度的代价（一次自我纠正）**　最初按「页跨度 ÷ 页内条数」算出 ±1.7 小时，
**这个数是错的**——它假设页内均匀分布，而真实收藏是成簇的（刷十分钟连收五条，
然后隔一天）。实测 40 条里 4 条被插值推到了发布时间**之前**，最多早 8.7 小时。
加了三个约束后归零：收藏 ≥ 发布、收藏 ≤ 本页上界、下限沿列表顺序向上传播
（第三条不只是让顺序单调——某条的发布下限对它上面所有条目同样成立，是白捡的信息）。

真正的保证只有一条：**每条落在它所属那一页的区间内**，宽度 9~34 小时，
收藏稀疏的年份更宽。够做文件名的日期前缀，不够做别的推断。

**连带**　`first_seen` 的注释从「≈ 收藏时间」改成明确的「不是收藏时间」；
`collected_at` 用 `COALESCE(items.collected_at, excluded.collected_at)` 只认第一次算出的值——
页边界每次扫描落点不同，天天覆盖等于让收藏时刻天天变，文件名也跟着变。

### 笔记格式定稿：`分类` 归档、`标签` 检索，两者都不进对方的地盘

**改动**　新增 [`第三段-笔记规格.md`](第三段-笔记规格.md) 作为笔记格式的权威定义；
[`旧版-单条链接流程与笔记模板.md`](旧版-单条链接流程与笔记模板.md) 打上归档标记，降为留档。

**从什么改到什么**

```
旧模板   只有自由 `标签`，账本的 category / decay 没人填、idx_category 是个空索引
现在     分类（一篇一个，进账本）+ 时效（四档固定，进账本）+ 标签（多个，只在笔记里）
```

**为什么这么切**　判断标准只有一条：**会不会想在「不打开笔记」的前提下按它捞出一批。**
「把所有 `decay=fast` 的重新过一遍」要在账本里 SELECT，所以 `分类`／`时效` 必须双写；
「找所有讲 RAG 的」是全文检索，ripgrep 和 Obsidian 干得比 SQLite 好，所以 `标签` 不进账本。

标签不进账本还有实测支撑：账本 48 条标题里 47 条自带作者话题，**127 个不重复标签 / 48 条**，
且全是同义词碎片（`#ai`／`#AI`／`#人工智能` 三种写法，某手游的话题有四种写法）。
外推到 5831 条是几千个标签，塞进一列 TEXT 既建不了有效索引也查不准。

**代价**　`分类`／`时效` 双写会漂移：手改笔记后账本不知道。
约定**笔记是真相、账本是缓存**，将来加 `--resync` 从 frontmatter 回灌，现在不做。

### `category` 的四个固定值撤销，改成先自由填

**改动**　`AI技术 / 游戏攻略 / 生活方式 / 其他` 不再作为封闭选项，第三段让 LLM 自由填一个词，
攒够 200 条看真实分布再锁定列表。

**为什么**　拿账本里 48 条真实标题试分，**最大的桶是「其他」占 38%**，
而且那里面不是噪音，是成团的漏类：摄影修图 4、影视娱乐 4、手工艺术 4、硬核工程 3。
一个分类体系里最大的桶叫「其他」，说明这个体系是错的。
48 条只是 5831 条的 0.8%，现在拍板必然还得推翻。

**代价**　几乎没有：`category TEXT` 本来就没有 CHECK 约束，那四个值只写在注释里，
schema 不用动；自由填也不额外花钱，是同一次 LLM 调用里的事。

### 删掉「纠正 whisper 专名错误」这条提炼指令

**为什么记这一条**　它标记了一个设计假设的死亡：**转写错误该在源头解决，不该让下游每篇都擦一次屁股。**
同一条视频、真值取自画面硬字幕，whisper 8 个专名全错，qwen 带热词只错 1 个——

### 澄清：`sync.mjs` 不调用 `extract.mjs`

**改动**　第一段的入口只管采集，不串第二段。README 里「唯一入口」的说法一并改掉。

**为什么记这一条**　这不是新决策，而是**纠正一次自己的跑偏**。
架构从一开始就写着两段分离、各有定时器，但在讨论「怎么手动跑通全链路」时，
我把两件事混为一谈了：

```
需求      能用手动的方式跑通全链路
误解成    把全链路塞进一个进程
```

合并会具体损失什么：登录态失效时 `sync.mjs` 在第一步就 `die(4)` 退出，
永远走不到提取——而账本里可能还躺着几十条已下载待转写的，
它们完全不受登录影响。这正是当初写「采集挂了不该影响提取（还有积压可做）」
要防的那件事。

而且合并会让账本的角色被架空：账本存在的意义就是当两段之间唯一的接口，
再加一条直接调用就成了双重耦合。

**正确形态**　手动跑全链路 = 依次跑两条命令；以后两个定时器跑的是同样这两条。
手动与自动之间不改任何代码——这才是「分离 ≠ 手动」的真正含义。

### `reconcile()` 加两道硬闸

**改动**　从「可以裸调」变成「必须显式声明全量扫描，且删除比例超阈值就拒绝」。

**为什么**　这是全项目最危险的一个函数——它按「不在名单里」判死，

早期滚动容器找错导致扫描只返回 69 条却一切正常地退出，正是这种。
没有这道闸，一次静默的扫描故障就会毁掉整本账。

### 修一个潜伏的 stdout 截断 bug

**改动**　`get_collection.mjs` / `get_meta.mjs` 输出 JSON 后不再立刻
`process.exit()`，改为等写入回调触发再退出。

**为什么记进架构变更**　它推翻了一个隐含假设：**「子进程的输出总是完整的」**。

```js
console.log(JSON.stringify(bigObject));
process.exit(0);                          // ← stdout 是管道时，没写完的部分直接丢弃
```

stdout 是管道时写入是异步的，超过缓冲区（macOS 64 KB）的部分排队等待，
而 `process.exit()` 立刻终止进程。结果是一个**正好 65536 字节、被腰斩的 JSON**。

这个坑潜伏了很久，因为它只在被父进程用管道接收时才出现——直接跑到终端（TTY）
或 shell 重定向到文件都是同步写，看不出问题。所以它一直等到
`sync.mjs` 第一次接管扫描输出才暴露。

**如果没在这时候撞上**，`node sync.mjs --init` 扫 5831 条时 coll.json 会在
64 KB 处被腰斩，下游要么解析失败、要么只处理其中一小部分。

### mp4 清理策略定案

**决定**　转写完成后**保留 7 天再删**；删之前**不存关键帧**。
连带**废掉「只有到 `extracted` 才可删」这条旧规则**。

**为什么废掉 `extracted` 闸门**　它的唯一理由是 OCR 增强要靠 mp4 抽帧，
而关键帧方案在同一次决定里被否了——理由没了，规则不该留着。何况第三段
消费的是 `.txt`，根本不碰 mp4；绑着它只会让第二段的磁盘占用被第三段的进度
绑架：第三段一天不开工，`extracted` 就一天到不了，等于一个 mp4 都删不掉。

**为什么留 7 天**　转写质量目前只在少量样本上验证过，热词表也还在长。
删早了发现问题就得重新下载，而 CDN 地址会过期，等于要重新扫描一遍。

**为什么不存关键帧**　存 12 张（约 1 MB/条，全量约 4.7 GB）本意是给未来的
OCR 增强留原料，但实测关键帧对屏幕录制会漏 73%——**这个保险不保靠**，
不值得为它长期占 4.7 GB。将来真做 OCR 时按需重下。

### 端点选择定案：留在同步，接受切片

**改动**　确认不迁移到异步端点（`fun-asr`、`*-filetrans`），保留 290 秒切片逻辑。

**为什么**　异步端点不限音频时长，看起来能省掉切片代码。但故障面差距悬殊：

```
同步   请求 → 结果                                     1 处会挂
异步   换凭证 → 传 OSS → 提交 → 轮询 → 取结果 URL → 下载   8 处会挂
```

这段代码跑在**凌晨 3:30 无人值守**——多出来的分支平时不执行，
只在半夜出问题时第一次被真正跑到。异步还有个悬而未决的问题：轮询多久算超时。

切片的代价则小得多：超 290 秒的只占 9%，日常摊下来每天约 1.1 条，
且是纯本地确定性操作，接缝按静音中点下刀实测不劈词。

**翻转条件**　如果把 10 分钟的下载上限大幅放宽（比如到 60 分钟），
每条就是 13 次请求、13 个独立失败点，届时异步的单任务更稳。

### 状态机：6 态 → 7 态，新增 `transcribed`

**改动**　`downloaded → extracted` 之间插入 `transcribed`。

**为什么**　转写（ASR，机器干的）和提炼（LLM 写笔记，prompt 说了算）

但全量 5831 条之后重扫一次要十几分钟，不能再那么干。

## 2026-09-01

### 提取路径：抽帧 + 本地 OCR + 多模态 → 纯云端 ASR

**这是本项目至今最大的架构改动。**

**原方案**

```
密集抽帧（约 210 帧/条）──→ 本地 Vision OCR ──→ 字幕文本 ─┐
                                                        ├─→ 一次多模态调用 ─→ 笔记
关键帧 12 张（场景切变 + 感知哈希去重）───────────────────┘
```

**现方案**

```
剥音轨 ──→ 云端 ASR ──→ 转写稿 ──→（提炼笔记，尚未实现）
```

**为什么**

原方案的核心假设是「**硬字幕是内容的主要载体，本地 OCR 读它就够**」。
这个假设有一半是错的：

1. **本地 OCR 读的是字幕，而字幕只占屏幕文字的一小部分。**
   实测逐帧 OCR 出的 467 个片段里，只有 35 个是字幕。
2. **关键帧漏得厉害。** 屏幕录制是连续滚动的，场景检测抓不住渐变，实测漏 73%。
3. **密度差 130 倍。** 纯口播那条逐帧跑 13.6 秒只换来 105 字，
   而屏幕录制那条有 13890 字。一刀切的抽帧策略两头不讨好。

同时用户明确要求「**先只用 ASR 来简单一点**」。

**OCR 没有被否定，而是被重新定位**：它的职责从「捞硬字幕（必需路径）」
变成「捞屏幕文字（可选增强）」。ASR 已经覆盖了口播内容，OCR 要解决的是
ASR 天生拿不到的那部分——实测一条屏幕录制视频 ASR 171 字 vs OCR 9396 字。
依据与实现方案完整保留在 [`待办-OCR增强.md`](待办-OCR增强.md)。

**提交**　`d8ffec8`

### 状态载体：文件系统 → SQLite 账本

**改动**　新增 `scripts/ledger.mjs`。

**为什么**　v0.1.0 的「状态」全靠文件系统——「media 目录里有没有这个文件夹」

- 哪些下好了但还没提取？
- 哪些提取失败了、失败几次了、还该不该重试？
- 哪些提取完了、mp4 可以删了？（**按状态删而不是按时间删**）
- 哪些是主动跳过的（图集 / 超长）？
- 哪些已经从收藏夹里被移除了？

**为什么是 SQLite 而不是 JSON**　五千条量级下 JSON 每次都要全量读写；
而这里最频繁的操作是「按状态查一批」，正是索引擅长的事。
另外两个定时任务可能重叠，SQLite 的事务比手工读写 JSON 安全。
用 Node 22 内置的 `node:sqlite`，零依赖。

### 项目形态：Skill → 独立脚本 + 单一入口

**改动**　不做成 Claude Code Skill，改为普通 Node 脚本 + `sync.mjs` 统一入口。

让 launchd 那一行只需要写 `node sync.mjs`。
