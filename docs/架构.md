## 三段 + 一本账

整个系统分三段，中间靠一本账衔接。

```
┌────────────────────── index.sqlite 账本 ──────────────────────┐
│   每条素材的身份、状态、产物位置、AI 判断结果、失败计数           │
└───────────────────────────────────────────────────────────────┘
        ▲                      ▲                     ▲
┌─────────────────┐    ┌───────────────────┐    ┌───────────────┐
│ ① 采集          │    │ ② 提取            │    │ ③ 提炼        │
│ sync.mjs        │    │ extract.mjs       │    │ notes.mjs     │
│                 │    │                   │    │               │
│ 扫收藏夹        │    │ 删过期 mp4        │    │ 读 .txt       │
│ 按账本筛 pending│    │ 剥音轨 + 静音切片 │    │ LLM 写笔记    │
│ 下载带音轨的档  │    │ 云端 ASR          │    │ 写 vault      │
│ 还原收藏时刻    │    │ 写 .txt           │    │ 写账本        │
│ 写账本          │    │                   │    │               │
│ ✅ 已打通       │    │ ✅ 已打通         │    │ ✅ 已打通     │
└─────────────────┘    └───────────────────┘    └───────────────┘
   约 28 秒/天            约 1.4 秒/条            约 20 秒/篇
```

跨条目的事（索引、去重、知识图谱）不在这三段里，是再往后一个阶段。
第三段严格 1:1:1——一条视频 → 一份转写稿 → 一篇笔记。

### 阶段骨架

加锁、日志落盘、运行记录、系统通知、退出码、磁盘检查这一套，
抽在 `scripts/stage.mjs` 里两段共用。**每个阶段有自己的锁**
（`.lock.collect` / `.lock.extract`），不共用——两段本来就该能重叠跑：
采集在下新的，提取在转积压的，互不干扰。账本开了 WAL，并发读写安全；
而且条目只有在 mp4 完整落盘之后才会被标成 `downloaded`，
提取不会捞到写了一半的文件。

退出码约定，定时任务据此决定要不要告警：

```
0 成功   1 出错   3 同阶段已在跑   4 登录态失效（仅采集）   5 磁盘不可用   6 缺配置
```

运行记录落在 `~/.dustoff/runs/<时间戳>-<阶段>/`，目录**惰性创建**——
被锁挡下的那次不该留一个空目录。

### 账本筛在扫描和下载之间

```
get_collection.mjs → coll.json（这一轮扫到的全部）
                        ↓
                     importScan → 账本
                        ↓
                  ★ 按账本筛 → todo.json（只留 status='pending'）
                        ↓
                     download.mjs（无脑下 todo.json 里的全部）
```

**为什么需要这一步**：`download.mjs` 只会问磁盘「文件在不在」，而磁盘的「不在」
是个歧义答案——分不清「从没下过」和「转写完被正常清理了」。后者如果重下，
会形成一个循环：

```
下载 → 转写 → 保留期到了删掉 → 但它还在扫描窗口里 → 又被下回来 → …
```

扫描窗口（200 条 ≈ 13 天）比保留期（7 天）长，**所以每一条都会中招**，
等于每 7 天白下一遍。

由账本来筛，`download.mjs` 就仍然只管「给我什么下什么」，不必认识账本。

**只放行 `pending`，没有例外。** 文件不在就是不在，不追究原因——
用户手工删掉的东西，工具不该自作主张下回来。

### 三段各有各的入口，互不调用

```bash
node sync.mjs        ① 采集：扫描 → 下载 → 写账本
node extract.mjs     ② 提取：清理过期 mp4 → 转写 → 写账本
node notes.mjs       ③ 提炼：读转写稿 → LLM 写笔记 → 写账本
```

三个入口都在项目根目录，跟 `scripts/` 下被调用的零件分开——
目录层级要能直接读出「有几个入口」，不必翻文档。

三条命令各自独立、各自幂等，**只通过账本对话**——采集写 `pending`/`downloaded`，
提取读 `downloaded` 写 `transcribed`，提炼读 `transcribed` 写 `extracted`。
手动跑全链路就是依次执行这三条；以后 launchd 定时器跑的也是同样这三条，
手动和自动之间不改任何代码。

`sync.mjs` 刻意不调用 `extract.mjs`。合并成一个进程会废掉故障隔离：
登录态失效时采集在第一步就退出，而账本里可能还躺着一批已下载待转写的，
它们本来完全不受登录影响。而且那样会变成「既有直接调用、又有共享账本」的
双重耦合，账本这层抽象就白做了。

**第三段为什么够格算独立一段**（早期曾判断它不够格，那个判断错了）：
它有自己的失败域（LLM 挂了不影响采集和提取）、自己的重跑节奏
（prompt 要改很多轮，而 ASR 一次就够）、自己的计费口子。
把它并进第二段的话，改一版 prompt 就得连 ASR 一起重跑，等于为改提示词重复付转写的钱。

## 状态机

```
(新扫到) ──→ pending ──┬──→ downloaded ──┬──→ transcribed ──┬──→ extracted  笔记已生成
                       │                 │                  └──→ failed     提炼重试超限
                       │                 └──→ failed         转写重试超限
                       ├──→ skipped      主动跳过，带 skip_reason
                       └──→ failed       下载重试超限

任何状态 ──→ removed   对账时发现已不在收藏夹里
```

**为什么 `transcribed` 和 `extracted` 要分开：** 转写（ASR，机器干的）和提炼
（LLM 写笔记，prompt 说了算）失败原因不同、重跑代价也不同。合成一个状态的话，
笔记模板一改就得连 ASR 一起重跑，等于为改 prompt 重复付一次转写的钱。

另外 **mp4 不等 `extracted`——`transcribed` 之后保留 7 天就删**。
第三段消费的是 `.txt`，根本不碰 mp4；把删除权绑在一个不消费它的阶段上，
只会让第二段的磁盘占用被第三段的进度绑架。详见「mp4 的清理策略」。

`skipped` 是状态而非标记，这样将来想捞某条超长视频，
直接 `requeue` 改回 `pending` 即可，不用改表结构。
第三段判「转写稿撑不起一篇笔记」也走这里（`skip_reason='need_ocr'` + `needs_ocr=1`），
那不是失败是缺料——OCR 补完画面文字再退回 `transcribed` 重走一遍。
**规则里没有「因为题材不高级所以扔掉」这一条**，收藏这个动作本身就是信号。

## 为什么是分离而不是流式

「下完一条立刻提取」听起来更顺，但不成立：

**故障域该隔离。** 采集挂了不该影响提取（还有积压可做），
提取挂了不该影响采集（明天照收）。

**提取批量做更准。** AI 一次看 20 条做分类，比逐条问 20 次准得多——
它能看到条目之间的相对关系。

### 分离 ≠ 手动

这是个容易混淆的点：**「两段是不是同一个进程」和「谁来触发」是正交的两件事。**

分离之后两段各有各的定时器，依然是全自动。
会话式提炼只在首轮用来打磨 prompt，不是最终形态。

## 提取：纯云端 ASR

**必须先下 mp4 再转。** 抖音不提供纯音频流，也没有字幕轨，
拿到声音的唯一途径就是从视频里剥。

**不用本地 whisper。** 同一条视频、真值取自画面硬字幕，8 个专名里
云端 ASR 错 1 个，本地 `whisper base` **全错 8 个**
（Claude Code→Cloud Code、时序图→实序图、重绘→重惠…）。
而云端一条 3.5 分钟的视频只要 ¥0.046。

### 模型：qwen-audio-3.0-asr-flash

走同步 `multimodal-generation` 端点，音频 base64 内联。
同价的 `qwen3-asr-flash` 也支持，改 `DUST_ASR_MODEL` 即可切换——
两族的请求与返回差异隔在 `extract.mjs` 的 `DIALECTS` 里。
完整选型依据见 [`ASR选型-2026-09-02.md`](ASR选型-2026-09-02.md)。

**热词是准确率的关键杠杆。** `~/.dustoff/asr-context.txt` 里的词会被优先识别：
不给热词认成 `cloud code`，给了就是 `Claude Code`。它还顺带管输出格式——
在表里的缩写输出干净（`SVG`），不在表里的会被拆成字母（`S V G`）。

### 为什么留在同步端点

异步端点（`fun-asr`、`*-filetrans`）不限音频时长，代价是故障面大得多：

```
同步   请求 → 结果                                     会挂的地方：1 处
异步   换凭证 → 传 OSS → 提交 → 轮询 → 取结果 URL → 下载   会挂的地方：8 处
```

这段代码跑在**凌晨 3:30 无人值守**。多出来的分支平时不执行，
只在半夜出问题时第一次被真正跑到——那是最不该有未验证代码的位置。

同步的代价是 **300 秒硬上限**，超了要自己切片。但这个代价很小：
超 290 秒的只占 9%，日常增量摊下来每天约 1.1 条，而且切片是纯本地的
确定性操作，跑一次验一次。接缝按静音中点下刀，实测不劈词。

**什么情况下该翻过来：** 如果把 10 分钟的下载上限大幅放宽（比如到 60 分钟），
那就是每条 13 次请求、13 个独立失败点，成功率反而不如异步的单个任务。

### mp4 的清理策略

**转写完成后保留 7 天再删。** 不立即删的理由：转写质量目前只在少量样本上
验证过，热词表也还在长；删早了发现问题就得重新下载，而 CDN 地址会过期，
等于要重新扫描一遍。

保留期从 `transcribed_at` 算，**不能用 `updated_at`**——每天的扫描都会刷新
后者，只要条目还在收藏夹里就永远显示「刚动过」，mp4 就永远删不掉。

清理跑在每轮转写的**开头**，腾出来的空间本轮就能用；即使本轮转写失败，
清理也已经做了。两条安全规则写死在代码里：转写稿必须真的在磁盘上
（账本说转过了不算数），以及 **0 字的不删**——那些是 ASR 什么也没听到的
纯画面视频，对它们来说视频本身仍是唯一的内容载体。

**删之前不存关键帧。** 存 12 张关键帧（约 1 MB/条，全量约 4.7 GB）本来是给
未来的 OCR 增强留原料，但实测关键帧对屏幕录制会漏 73%——这个保险不保靠，
不值得为它长期占 4.7 GB。将来真做 OCR 时按需重下。

**为什么不等 `extracted`。** 「笔记写完才能删」的唯一理由是 OCR 要靠 mp4 抽帧，
但抽帧方案已经被上面那条否掉了——**理由没了，规则却留着**。剩下的全是代价：
第三段一行代码都没有，`extracted` 永远到不了，等于一个 mp4 都删不掉，
而存量补完是 39 GB；何况笔记模板必然要推翻重写好几轮，那段时间条目全卡在
「转完了、笔记没定稿」，正是占用最高的时候。代价则是已经接受过的那条：
真做 OCR 时按需重下。

### 产物

```
$DUST_TEXT/<id>.txt          纯文本转写稿。保持纯净，text_chars 才诚实
$DUST_TEXT/<id>.words.json   逐词时间戳（模型给了才有），切片偏移已加回
$DUST_NOTES/<收藏日>-<主题>.md  笔记。frontmatter 指回转写稿路径
```

转写稿刻意不放 media 目录下——mp4 会被清理，文字稿要活得比它久。
笔记里两处指回原料（frontmatter 一行纯路径 + 末尾一行可点链接）：
笔记是派生物、改 prompt 随时能重生成，转写稿是花钱买的、不可再生。

## 无人值守时哪些情况需要人

| 情况 | 处理 |
|---|---|
| 登录失效 | ✅ 标记文件 + 系统通知 |
| 磁盘不足 | ✅ 阈值告警 |
| 连续转写失败 | ✅ 连续 5 条即中止整轮（止损闸，防止余额耗尽时把几千条挨个撞一遍） |
| 失败原因是什么 | ⬜ 待做：中止了但不知道是 key 失效、余额不足还是限流 |
| 提取失败率异常 | ⬜ 待做 |
| 单条重试超限 | ✅ 标 `failed` 不再重试 |
| `reconcile` 误判 | ✅ 两道硬闸：调用方必须显式声明「这是全量扫描」，且单轮移除量超 10% 直接拒绝执行 |
| 笔记质量漂移 | 只能靠定期抽查 |

**定时器排在最后不是笔误。** 现在就接上，每天只会自动囤一批没人消费的产物；
而且 prompt 还要反复改，正需要手动控制节奏。存量补录同理——
prompt 没定稿就补 5831 条，等于按一版必然要推翻的格式生产几千篇笔记。

笔记提炼整体在第三阶段——**第二段的出口就是语音转文字的 `.txt`**，到此为止。
这样第二段有一个干净、可验证的终点，不必等笔记格式定稿。

### 第三段：格式已定稿，代码没开工

笔记长什么样、字段落在哪、prompt 要求什么，全部写在
[`第三段-笔记规格.md`](第三段-笔记规格.md)。这里只留一条架构层面的结论。

**开工前真正要回答的不是「怎么写笔记」，而是「哪些配写笔记」。** 已转写的 12 条实测分布：

```
3295 字  硬核技术长课            ┐
1454 字  技巧类教学              │ 值得成篇
1010 字  职业方法论              │
 739 字  工具介绍                ┘
──────────────────────────────
 337 字  游戏攻略                ┐
 262 字  段子合拍                │
 172 字  影视片段                │ 一半以上不该进知识库
 144 字  带货口播                │
 103 字  技巧演示                │
  51 字  景区互动                ┘
   0 字  纯画面无人声（ASR 空）
```

收藏夹不等于知识库。没有筛选就直接提炼，等于给一条带货口播认真生成一篇
带标签的 Markdown，还为此付一次 LLM 的钱。

但光看字数会误判——最短的 337 字那条（58 秒阵容攻略）信息密度反而最高。
所以准入分两层：脚本用 `text_chars < 50` 免费挡掉一批，剩下的让 LLM
在提炼的同一次调用里顺带判断值不值得收录（转写稿反正要发过去，多回一个布尔值是白送的）。
