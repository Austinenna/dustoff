# dustoff 架构

> 2026-09-01。定稿于 v0.1.0 之后、着手第二段之前。

## 三段 + 一本账

整个系统分三段，中间靠一本账衔接。

```
┌────────────────────── index.sqlite 账本 ──────────────────────┐
│   每条素材的身份、状态、产物位置、AI 判断结果、失败计数           │
└───────────────────────────────────────────────────────────────┘
       ▲                        ▲                        ▲
┌──────┴─────────┐    ┌─────────┴────────┐    ┌─────────┴──────┐
│ ① 采集          │    │ ② 提取            │    │ ③ 组织          │
│ 定时 03:00      │ →  │ 定时 03:30        │ →  │ 暂缓            │
│                │    │                   │    │                │
│ 扫收藏夹        │    │ 抽帧（本地）        │    │ 索引            │
│ 下载最低码率档   │    │ OCR（本地 Vision） │    │ 去重            │
│ 写账本 pending  │    │ 多模态提炼（云端）   │    │ 关联 / 图谱      │
│                │    │ 写笔记 → vault     │    │                │
│                │    │ 删 mp4，留关键帧    │    │                │
│ ✅ v0.1.0 完成  │    │ 开发中              │    │ 以后            │
└────────────────┘    └───────────────────┘    └────────────────┘
   约 28 秒/天              约 4 分钟/天             手动
```

**第三段现在不做。** 在不做跨条目关联的前提下，「归档」只是把文件写进 vault，那是第二段的收尾动作，不构成独立阶段。等笔记攒到需要索引、去重、找关联时，第三段才有独立存在的理由。

## 为什么是分离而不是流式

「下完一条立刻提取」听起来更顺，但不成立：

**速度差 40 倍。** 下载一条约 0.5 秒，提取一条约 20 秒（OCR 3× 实时）。绑在一起，下载会被提取拖死——日常 10 条新视频，分离模式 7 秒下完，流式要等 200 秒。

**故障域该隔离。** 采集挂了不该影响提取（还有积压可做），提取挂了不该影响采集（明天照收）。

**提取批量做更准。** AI 一次看 20 条做分类，比逐条问 20 次准得多——它能看到条目之间的相对关系。

### 分离 ≠ 手动

这是个容易混淆的点：**「两段是不是同一个进程」和「谁来触发」是正交的两件事。**

分离之后两段各有各的定时器，依然是全自动。会话式提炼只在首轮用来打磨 prompt，不是最终形态。

## 提取为什么是本地 + 云端混合

分清哪一步云端不可替代：

| | 本地 Vision OCR | 云端多模态 |
|---|---|---|
| 读硬字幕 | 实测几乎全对 | 一样对，但贵 7 倍 |
| 看懂白板 / 图表 / 代码截图 | ❌ 只能读字 | ✅ 唯一不可替代之处 |

密集抽帧是为了不漏字幕——一条 3.5 分钟视频约 210 帧。这 210 帧全走云端，成本翻 7 倍而准确度毫无提升，因为硬字幕是高对比度印刷体，本地 OCR 已经打满。

而写笔记这一步本来就要调 LLM，现代 LLM 又是多模态的，所以**把 12 张关键帧直接塞进那次调用**，一次完成「看图 + 读文本 + 写笔记」，不需要单独的 OCR 服务环节。

```
密集帧 ──→ 本地 Vision OCR ──→ 字幕文本 ─┐
                                        ├─→ 一次多模态调用 ─→ 笔记
关键帧 12 张（场景切变 + 感知哈希去重）───┘
```

单条成本约 0.042 元。日常增量约 13 元/月。

关键帧**不随 mp4 一起删**——白板推导、代码截图、图表，图本身比 OCR 出来的文字更有价值，而且 12 张只占约 1 MB。

## 无人值守时哪些情况需要人

| 情况 | 处理 |
|---|---|
| 登录失效 | ✅ 标记文件 + 系统通知 |
| 磁盘不足 | ✅ 阈值告警 |
| 提取失败率异常 | 待做 |
| API 余额不足 / 报错 | 待做：告警并停止重试，别烧钱 |
| 单条重试超限 | 待做：标 `failed` 不再重试，列出来 |
| 笔记质量漂移 | 只能靠定期抽查 |

## 路线

```
0.2  账本（SQLite）              三段都依赖它，起点
0.3  抽帧 + 本地 OCR + whisper 兜底
0.4  会话式跑十几条，定笔记格式与 prompt   ← 别跳过
0.5  切云端 API 全自动 + 失败告警 + 按状态删 mp4
1.0  两个 launchd 定时器接上，端到端无人值守
```

**0.4 不能跳。** prompt 在真实数据上打磨过再上自动化，否则批量跑出一堆格式不对的笔记，重跑要再花一次钱。
