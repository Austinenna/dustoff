# 第三段：笔记规格

> 这是**笔记长什么样**的权威定义，第三段的 prompt 从这里生成。
> 前身是 [`旧版-单条链接流程与笔记模板.md`](旧版-单条链接流程与笔记模板.md)——
> 那是一份 whisper 时代的 Claude Skill，靠对话触发、Claude 亲手读写文件。
> 现在整条链路是脚本，输入变成账本里的 `.txt`，输出要机器可解析，
> 所以模板不能照抄，得重写一遍。文末列了具体改了哪些。

## 边界：严格 1 : 1 : 1

```
一条视频  ──→  一份 ASR 转写稿  ──→  一篇笔记
```

不合并、不拆分、不做跨条目关联。去重、找关联、知识图谱都是**再往后一个阶段**的事，
这里一律不碰。判断某个想法该不该进来，只问一句：**它需要读第二条视频吗？**
需要，就不属于第三段。

## 一、谁配写笔记

**收藏夹不等于知识库。** 已转写的 12 条里，一半以上不该进：带货口播、
段子合拍、景区互动台词。没有准入判断就直接提炼，等于给广告认真生成一篇
带标签的 Markdown，还为此付一次 LLM 的钱。

但**光看字数会误判**。实测里最短的一条反而信息密度最高：

```
 337 字  一条游戏攻略      58 秒，句句是干货，笔记写得比 1010 字那条还长
 144 字  一条带货口播      纯口播，一句有用的没有
```

所以准入分两层：

| 层 | 判断者 | 规则 | 代价 |
|---|---|---|---|
| 硬门槛 | 脚本 | `text_chars < 50` 直接不送 LLM | 免费 |
| 软判断 | LLM | 同一次调用里顺带输出「材料够不够写一篇」 | 已经付过了 |

软判断不额外花钱——反正要把转写稿发过去，让它多回一个布尔值是白送的。

> ### 判断的是「材料够不够」，不是「配不配」
>
> **收藏这个动作本身就是信号。** 你主动存了它，就说明它对你有用；
> 让 LLM 去替你判断某条「不够格进知识库」，是在替你做品味判断——那不是它的活。
>
> 所以软判断只回答一个事实问题：**这份转写稿能不能撑起一篇笔记。**
> 撑不起的**不是扔掉，是标 `needs_ocr = 1` 进补料队列**：
>
> ```
> 144 字的带货视频     不是「广告所以不要」
>                     是「型号和链接都在画面上，ASR 只录到了口播」
>                     → needs_ocr = 1，等 OCR 补完再写笔记
> ```
>
> 落 `skipped` + `skip_reason = 'need_ocr'`，OCR 那一轮跑完退回 `transcribed` 重走提炼。
> **规则里从来没有「因为题材不高级所以扔掉」这一条。**

## 二、笔记格式

### frontmatter

> **字符串值一律加引号，日期不加。** 抖音的 aweme_id 是 19 位数，不加引号的话
> YAML 解析器按整数读，而它超过 JS 安全整数上限（2^53），转 float64 末几位就丢——
> `7676650803859361059` 会变成 `7676650803859360768`。文件里字是对的，
> 但 Obsidian Dataview、自己写的脚本读到的全是错 ID，而且不报错。
> 标题和作者同理（半角冒号、井号会把 YAML 拆坏）。日期故意留裸值，
> 好让 Obsidian 认成日期类型能排序能筛。

```yaml
---
标题: <凝练的主题标题，不抄原标题的标题党写法>
来源: 抖音
作者: <author>
视频ID: <aweme_id>
链接: https://www.douyin.com/video/<aweme_id>
发布日期: <账本 created_at → YYYY-MM-DD>      # 作者什么时候发的
收藏日期: <账本 collected_at → YYYY-MM-DD>    # 我什么时候收藏的（估计值，见下）
提炼日期: <生成这篇笔记的那天 → YYYY-MM-DD>    # 见下
时长: <duration_s → X分X秒>
转写稿: <账本 text_path>                       # 回源用，见下
分类: <一个词，见下>
时效: <none | slow | fast | event>
标签: [<3-6 个关键词>]
---
```

**三个日期，各自回答不同的问题**：作者哪天发的 / 我哪天存的 / 这篇笔记哪天写的。
下载日期不要——它跟收藏日期只差 0~1 天（当天扫到当天下），是条冗余信息。

`提炼日期` **每次重跑都会变，这正是它的价值**：prompt 会反复改、同一份转写稿会被
重新提炼很多轮，这个日期说的是「这篇笔记反映的是哪一版的理解」。
另外两个日期都是历史事实、永远不动，只有它跟着当前的想法走。

叫「提炼」不叫「提取」：`提取` 是第二段（ASR）的名字，占用它会真的混淆。

**笔记末尾还有一行回源页脚**：`[转写稿](file://…) · [原视频](https://…)`。
frontmatter 里那行是纯路径（好复制、好被程序读），页脚是可点链接。
两处都要——**笔记是派生物，改 prompt 随时能重生成；转写稿是花钱买的、不可再生**。
读笔记时想核对原话，不该还要去猜文件在哪，更不该切到项目目录敲命令。

想要「哪一句在第几秒」用 `node scripts/timeline.mjs <id>`，
它把 `.txt` 和 `.words.json` 合成分句时间戳视图，按需生成、不占存储。

**`分类` 和 `标签` 不重复，是两种东西：**

```
分类   一篇只有一个，回答「这归到哪个架子上」   → 归档，要能批量筛
标签   一篇好几个，等同论文的 keywords         → 检索，要能全文搜
```

**`分类` 暂时让 AI 自由填**，不给固定选项。理由是现有的四个值撑不住——
拿账本里 48 条真实标题试分，最大的桶是「其他」占 38%，而且那里面不是噪音，
是成团的漏类（摄影修图 4、影视娱乐 4、手工艺术 4、硬核工程 3）。
**一个分类体系里最大的桶叫「其他」，说明这个体系是错的。**
48 条只是 5831 条的 0.8%，现在拍板必然还得改。
先自由填，**攒够 200 条看真实分布再锁定列表**——不额外花钱，拿到的是真数据。

> 账本里 `category TEXT` 没有 CHECK 约束，那四个值只写在注释里，
> 数据库本来就什么字符串都收。自由填不需要改 schema。

**`时效` 四档固定**，语义正交，不用改：

| 值 | 含义 | 例 |
|---|---|---|
| `none` | 不过期 | 物理公式、方法论、审美判断 |
| `slow` | 年为单位 | 工具用法、职业建议、行业格局 |
| `fast` | 月为单位 | 软件版本、游戏版本、模型排名 |
| `event` | 绑死某个时间点 | 发布会、活动、节日、新闻 |

### 正文

```markdown
# 核心观点
<2-4 句话讲清这个视频到底说了什么、最有价值的点是什么>

## <分论点小标题>
<结构化要点，可用列表/表格>

## 结论
<视频的落脚点 / 给观众的 takeaway>
```

**长度按信息密度定，不按视频时长定。** 一分钟的攻略可以比四分钟的
泛泛而谈写得长，因为前者句句是干货、后者有一半是铺垫。

**总体控制在「适中」**——不设硬性字数，但别为了凑长度注水，也别把有用的细节压掉。
密度高的可以长，密度低的就该短。

### 文件名

`YYYY-MM-DD-<简短主题>.md`，日期用**收藏日**（`collected_at`）。

**重新生成时沿用已有文件名，不跟着新标题变。** 标题是模型每次现写的——实测
同一批跑两次，10 篇里 8 篇标题不一样（同一条视频，两次起的名字毫无重合）。
文件名要是跟着标题走，改一版 prompt 重跑就多出一整套文件、旧的全成孤儿，
而打磨 prompt 正是要反复重跑的事。名字是身份，内容才是产物。
第一次起坏了想改，加 `--rename`。
落在 `DUST_NOTES`（默认 `~/Documents/抖音收藏`）。

**为什么是收藏日不是发布日：** 人记得住的是「我什么时候存的」，记不住「作者什么时候发的」。
而且收藏这个动作本身携带信息——不管视频多老，我是那天存的，就说明那天它对我有用。

> ### 收藏时刻是估计值，别当精确时刻用
>
> 抖音的逐条对象里**没有**收藏时间——132 个字段全查过，时间戳只有 `create_time`（发布）、
> `mix_info.*`（合集）、`play_progress.last_modified_time`（我看到哪儿了）。
>
> 唯一的来源是 listcollection 响应**顶层的 `cursor`**：微秒级 unix 时间戳，
> 等于**这一页最后一条的收藏时刻**，逐页严格递减。已验证：账本里「昨天扫描之后才新增」
> 的 8 条全部落在第 1 页，一条不落。
>
> **精度：只有页边界是准的。** 每页最后一条精确到秒；页内其余按位次插值，
> 再用三个约束收紧（收藏 ≥ 发布、收藏 ≤ 本页上界、下限沿列表顺序向上传播）。
> 真正的保证只有一条：**每条落在它所属那一页的区间内**——抖音一页 10 条，
> 页跨度实测 9~34 小时，收藏稀疏的年份会更宽。
>
> 所以它回答的是「大致哪天存的」，够做文件名前缀，**别拿它做别的推断**。
>
> 实施在 `get_collection.mjs` 的 `assignCollectedAt()`，账本列 `collected_at`。
> 注意跟 `first_seen` 分开：后者是「我哪天扫到的」，存量补录时几千条会共用同一天。
>
> **存量要靠一次新的全量扫描拿。** 归档的 `collection-full-20260828.json` 里没有 cursor
> （当时就丢了），5831 条 ≈ 583 页 = 583 个精确锚点铺满整段历史——反正补存量本来也得扫一次。

## 三、字段去哪：笔记 vs 账本

判断标准只有一条：**你会不会想在「不打开笔记」的前提下，按这个字段捞出一批？**

| 字段 | 笔记 | 账本 | 为什么 |
|---|:--:|:--:|---|
| `分类` | ✅ | ✅ `category` | 要批量筛，得能 SELECT |
| `时效` | ✅ | ✅ `decay` | 同上：「版本更新了，把 fast 的重跑一遍」 |
| `标签` | ✅ | ❌ | 见下 |
| 笔记路径 | — | ✅ `note_path` | 账本要能找到文件 |

**标签坚决不进账本。** 账本里 47/48 条标题自带作者话题，实测 **127 个不重复标签 / 48 条**，
而且全是同义词碎片：`#ai`／`#AI`／`#人工智能` 是三种写法，
某手游的话题有四种写法（其中两个是纯 SEO 的活动 tag）。按这个比例外推到 5831 条是几千个标签，
塞进一列 TEXT 既建不了有效索引也查不准。自由关键词天生该待在 markdown 里，
交给 ripgrep / Obsidian 全文检索——那本来就比 SQLite 干得好。

**双写的一致性：** AI 一次输出，脚本一次写两处（写 md 文件 + `markExtracted()`），
同一步完成，正常不会漂。但你手改笔记里的分类，账本不知道。
原则是**笔记是真相，账本是缓存**；将来加个 `--resync` 从 frontmatter 回灌即可，现在不做。

## 四、提炼指令

给 LLM 的要求：

1. **重组，不复述。** 把口语流水账整理成结构化要点（核心观点／分论点／关键数据／结论），
   不是把转写稿断句排版。
2. **保留有信息量的具体内容**——数字、人名、产品名、金句，这些是笔记的价值所在。
3. **标题的 hashtag 是专名的地面真相。** ASR 常把专有名词听岔，而标题的 hashtag
   往往写着正确形式，按标题写。热词表覆盖不到的新词全靠这个兜底。

> **已删除：「纠正 whisper 同音／专名错误」。**
> 那条指令是 whisper 时代的补丁——同一条视频、真值取自画面硬字幕，
> whisper 8 个专名全错，qwen 带热词只错 1 个。错误已经在源头（`~/.dustoff/asr-context.txt`）
> 解决掉了，不该再让 LLM 每篇都做一遍无用功。
>
> 注意别把「结合标题 hashtag」这个动作一起删掉——它换了个身份留下来了，见上面第 3 条。

### 4. 引流内容：剔掉，但脚注写清推销的是什么

抖音「干货 + 卖课」的结构极其普遍。做法是剔出正文，在脚注里点名：

```markdown
> 视频后半段在推销作者的「2026 大模型学习路线图」，属于引流内容，未收录。
```

**判定标准是「推销物 ≠ 主题」，不是「出现了推销」。**

```
讲能力模型，最后卖路线图     推销物 ≠ 主题   → 引流，剔掉 + 脚注
整条就在讲那件商品           推销物 = 主题   → 这是正文，原样写
```

这条规则自带一个保险：**你要是就想收藏一个广告，那个广告一定是视频的主题，
按规则它就是正文，根本不会被剔。** 「讲 A 顺带卖 B」才叫引流。

第二重保险：**剔除不等于删除。** 脚注点了名（推销的是「2026 大模型学习路线图」），
所以哪怕误判，你看脚注也知道那是什么、能自己去找。误判的代价是多看一行，不是东西没了。

### 5. 转写稿够不到的信息：笔记里警告，账本里记账

阵容码、仓库地址、商品型号这类只在画面上的东西，ASR 一个字拿不到。

笔记里显式警告：

```markdown
> ⚠️ 视频说会给阵容码，但转写稿里没有——阵容码在画面上，ASR 拿不到。
```

**同时在账本记一笔 `needs_ocr = 1`。** 这一条是关键：光在 markdown 里写警告，
将来想「把所有缺料的挑出来集中做一次 OCR」就只能 grep 几千个文件；
记进账本才能 `SELECT ... WHERE needs_ocr = 1` 一次捞出来。

> 措辞要落在转写稿上。模型**只能看到转写稿、看不到画面**，所以不能写
> 「画面中也没有」这种它无法知道的话——`PROMPT` 里明确交代了这一点。
>
> **账本已加好这一列**（`ledger.mjs`，`markExtracted()` 负责写）：
> ```sql
> needs_ocr  INTEGER DEFAULT 0   -- 1 = 关键信息在画面上，ASR 拿不到，等 OCR 补料
> ```
> 一列就够，缺的具体是什么已经写在笔记的 ⚠️ 里了，不必在账本里再存一份文本。
> 没建索引：全表 5831 行的 `WHERE needs_ocr = 1` 是亚毫秒级，而这个查询一共也跑不了几次。
>
> 撑不起一篇的那种（材料几乎为零）走 `skipped` + `skip_reason = 'need_ocr'`，
> 同样带 `needs_ocr = 1`，两种情况将来一次捞干净。

## 五、改了 prompt 之后怎么办

账本记 `prompt_hash`——`PROMPT` 常量的 sha256 前 8 位，`markExtracted()` 写入。
改完提炼指令：

```bash
node notes.mjs --stale        # 只重跑笔记还停在旧版指令的那些
```

没有它就只能整批重来。虽然全量也才 ¥12，但分不清哪些重跑过、哪些没有，
是另一种代价——尤其是改到第三第四版时。

**只哈希 `PROMPT` 本身**，不含模型和 effort：把它们算进去的话，
做一次 effort 的 A/B 对照就会把全部笔记标成过期，那不是过期，是换了个档跑。

## 六、相对旧模板改了什么

| 旧版（Skill 时代） | 现在 | 原因 |
|---|---|---|
| Claude 读对话里的链接触发 | 脚本从账本 `claim('transcribed', N)` 批量取 | 不再是 skill，是自动化程序 |
| 输入 = `fetch.mjs` 的 stdout JSON | 输入 = 账本行 + `text_path` 指向的 `.txt` | 第二段已经把产物落盘了 |
| 本地 whisper 转写 | 云端 qwen-audio-3.0 + 热词表 | 见 [`ASR选型-2026-09-02.md`](ASR选型-2026-09-02.md) |
| 「纠正 whisper 专名错误」 | 删除；hashtag 改作专名地面真相 | 源头已解决 |
| 只有自由 `标签` | `分类` + `时效` + `标签` 三层 | 账本的 `category`／`decay` 需要有人填 |
| 无准入判断，来者不拒 | 硬门槛 + LLM 判「材料够不够」 | 撑不起一篇的进 OCR 补料队列，不扔 |
| 转写稿缺什么无处可记 | 账本 `needs_ocr` + 笔记 ⚠️ 脚注 | 缺料的要能一次捞出来集中补 |
| 文件名用发布日 | 文件名用收藏日 `first_seen` | 人记得住「我什么时候存的」 |
| frontmatter 只有发布日 | 发布／收藏／入库三个日期 | 各自回答不同的问题，再多就是噪音 |
| 输出 = Markdown 文件 | 输出 = Markdown 文件 **+** `markExtracted()` 回写账本 | 账本是唯一的跨阶段状态 |
| 存 `~/VideoKB/` | 存 `DUST_NOTES` | 配置化 |
