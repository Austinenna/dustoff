# ASR 选型：为什么是 qwen3-asr-flash

> 2026-09-02。起因是一个很实在的质疑：既然超过 10 分钟的视频都丢弃了，
> 那如果模型本身能吃 10 分钟，切片逻辑就是白写的。查下来结论比预想的复杂——
> 阿里的 ASR 分两套接口，能力和限制完全不同。

## 两套接口，不是一个货架上的东西

| | qwen3-asr-flash | fun-asr / paraformer-v2 |
|---|---|---|
| 端点 | `aigc/multimodal-generation` | `audio/asr/transcription` |
| 调用方式 | **同步**，一次往返 | **异步**：提交 → 轮询 |
| 输入 | base64 内联 | 文件 URL（`oss://` 或 `https://`） |
| 本地文件 | 直接塞进请求体 | 得先传到阿里临时空间 |
| 时长上限 | **< 300 秒**（实测 299 过、300 拒） | 至少 578 秒实测通过 |
| 热词 | 一段纯文本，随时改 | 需另调接口注册词表、管 ID |

两个 qwen3 型号在异步端点上都不可用（`qwen3-asr` 报 Model not exist，
`qwen3-asr-flash` 连官方示例 URL 都拒），所以「用 qwen3 的准确率 + 异步的
不限长」这条路走不通，只能二选一。

时长上限是实测二分出来的，不是抄文档：

```
181s ✓   240s ✓   270s ✓   290s ✓   298s ✓   299s ✓   300s ✗ "The audio is too long"
```

`audio_tokens` 恰好 25/秒，300×25 = 7500，是个整数上限。

## 准确率：paraformer 出局，另两个打平

同一条 9.6 分钟射频课（无人机 5.8G 图传），领域专名逐个数：

| | qwen3+热词 | fun-asr | paraformer-v2 |
|---|---|---|---|
| 图传 / ~~图层~~ | 5 / 0 | 5 / 0 | 4 / **1** |
| 设计动机 / ~~射计动机~~ | 1 / 0 | 1 / 0 | 0 / **1** |
| 公式 / ~~工序~~ | 6 / 0 | 6 / 0 | 0 / **5** |

**paraformer-v2 明显落后**，印证了官方「建议迁移」的说法。
最初选它只是因为照抄了 TokBrain 的配置，没有评估过。

qwen3 和 fun-asr 打平，差别只在缩写格式：qwen3 写成 `W I F I`、`S F P L`
（带空格，难看），fun-asr 写 `WiFi`。这一项后面提炼笔记时 LLM 会顺手抹平，
不构成选型依据。

## 决定性差异：热词

拿画面硬字幕当真值的 25 秒样本：

```
无热词  →  开源项目 diagram-design，专门给 cloud code 和 codex 用
有热词  →  开源项目 Diagram Design，专门给 Claude Code 和 Codex 用
                                        ^^^^^^^^^^^
```

`Claude Code` 这类专名在这个收藏夹里出现频率极高，认成 "cloud code"
会让后面的检索和分类全部落空。而热词只是 `~/.dustoff/asr-context.txt`
里的一行字，想到一个词就加一个。

fun-asr 也支持热词，但要走 vocabulary 注册接口、拿一个 ID 回来、
改词表得再调一次。同样的收益，多一套要维护的状态。

（`HTML` 被两个模型一致听成 `HPM`，热词也没救回来——大概率原音就含混，
不是模型的问题。）

## 结论：qwen-audio-3.0-asr-flash

**同步端点 + 热词 + 290 秒切片。** 模型选 `qwen-audio-3.0-asr-flash`。

### 为什么不是 qwen3-asr-flash

最初定的是 qwen3-asr-flash，后来发现同一个同步端点上还有更新的一族。
两者**同价（¥0.00022/秒，华北2）、同为 300 秒上限、热词机制相同**，
但 qwen-audio-3.0 多三样东西：

- **逐词时间戳。** qwen3 只给整段文本；qwen-audio-3.0 每个词带起止毫秒，
  笔记里能标「这句在第几秒」，回看原片可以直接跳。
- **更新的一代。** 从免费额度到期日（2026/10/27 减 90 天）反推是 2026 年 7 月
  发布；qwen3-asr-flash 的版本号是 2025-09-08 / 2026-02-10。
- **36,000 秒（10 小时）免费额度**，到 2026/10/27。qwen3-asr-flash 的
  90 天窗口已经过了。按日常增量约 1,280 秒/天算，这 10 小时够用 28 天。

押新一代还有个理由是抗淘汰——paraformer 就是老一代的下场：
官方标「建议迁移」，实测也确实明显更差。

### 两族的差异（已隔在 extract.mjs 的 DIALECTS 里）

| | qwen-audio-3.0-asr-flash | qwen3-asr-flash |
|---|---|---|
| 额外请求参数 | `parameters.format` 必传 | 无 |
| 取文本 | `output.text` | `output.choices[0].message.content[0].text` |
| 取计费秒数 | `usage.duration` | `usage.seconds` |
| 逐词时间戳 | `output.sentence.words[]` | 无 |
| 无人声时 | **HTTP 400** `ASR_RESPONSE_HAVE_NO_WORDS` | HTTP 200 + 空文本 |

最后一行是个坑：无人声不是失败，而是一个有效结论（这条视频纯画面）。
按错误处理会白重试三次、状态错标成 failed，而且这类条目
**正是 OCR 增强要挑的目标**，标成 failed 就再也进不了候选名单。

换模型只需改 `DUST_ASR_MODEL`，业务代码不动。

### 为什么留在同步端点

异步（fun-asr / *-filetrans）不限时长，代价是故障面大得多：

```
同步   请求 → 结果                                     会挂的地方：1 处
异步   换凭证 → 传 OSS → 提交 → 轮询 → 取结果 URL → 下载   会挂的地方：8 处
```

这段代码跑在**凌晨 3:30 无人值守**。多出来的分支平时不执行，
只在半夜出问题时第一次被真正跑到——那是最不该有未验证代码的位置。
异步还有个悬而未决的问题：轮询多久算超时。

切片的代价则小得多：超 290 秒的只占 9%（3203 条里 289 条），
日常增量摊下来每天约 1.1 条，而且是纯本地的确定性操作，跑一次验一次。
接缝按静音中点下刀，实测不劈词：

```
上段结尾: …就和 WIFI 的5745兆赫信道严重重叠。
下段开头: 产生同频干扰，这就是为什么跳频需要动态感知频谱占用。
```

**什么情况下该翻过来：** 如果把 10 分钟上限大幅放宽（比如到 60 分钟），
那就是每条 13 次请求、13 个独立失败点，成功率反而不如异步的单个任务。

## 单价（已核实）

`qwen-audio-3.0-asr-flash` 与 `qwen3-asr-flash` 同为 **¥0.00022 元/秒**
（华北2 北京；国际部署 ¥0.00026）。出处是模型详情页
`help.aliyun.com/zh/model-studio/qwen-audio-3-0-asr-flash`。

先从账单反推过一次，与官方完全吻合：

```
09-01 ¥0.39226 ÷ 0.00022 = 1783 秒 = 边界测试 1758s + 上一轮 25s   ✓
09-02 ¥0.11    ÷ 0.00022 = 500 秒  = 热词对比 25×3 + 批量 425s      ✓
```

换算：¥0.0132/分钟、¥0.792/小时（后两个是换算值，官方只写每秒单价）。

**查文档时的教训：** 大定价页（`billing-for-model-studio`）内容太多，
摘要式抓取会漏掉具体表格；**模型自己的详情页**窄而准，一次就拿到了。
另外，有真实账单的时候反推比查文档可靠。

### 成本估算

按 3913 条存档的真实分布（图集 14.2%、超 10 分钟 4.6%、均值 104 秒）：

| | 音频量 | 费用 |
|---|---|---|
| 日常增量（约 15 条/天） | 1,280 秒/天 | **¥0.28/天 ≈ ¥8.4/月** |
| 存量全量（5831 条外推） | 138 小时 | **约 ¥109**，一次性 |

免费额度 10 小时可覆盖 28 天日常增量，对存量只占 7%。

⚠️ 控制台里「免费额度用完即停」默认是关的，额度烧完会静默转按量计费。
