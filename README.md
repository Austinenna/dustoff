## 2026-09-19：本地图集

图集已接入日常收藏流程：采集每张图片地址 → 按原顺序下载 → 整组校验完成后保存。图集不调用用途模型、ASR、OCR 或笔记模型。

- 网页侧栏新增 **图集**，独立显示封面、张数和作者；支持搜索、分页、逐张查看、方向键切换及打开本地文件夹。
- 图片保存在 `DUST_SAVED_MEDIA/<作品 ID>/images/`，与视频共用收藏空间上限，不随转写缓存清理。每组计一条每日额度。
- 中途失败保留已完成图片，下轮只补缺失图片；整组完成前不会显示为已保存。图片的备用地址、实际格式和尺寸会验证。
- 正常运行会恢复此前仅因“不支持图集”而跳过的新收藏；历史基线不会自动下载。

## 2026-09-16：下载前用途分流

新增流程：扫描并记账 → 快速文本模型判断用途 → 选择下载规格 → 保存视频或转写笔记。
用途模型使用 `DUST_ROUTER_BASE` / `DUST_ROUTER_KEY` / `DUST_ROUTER_MODEL` 配置，支持本机 OpenAI 兼容网关。

- **保存视频**：优先最高分辨率档、同分辨率取较高码率，验证音轨；失败可回落平台默认播放档。保存后记为 `saved`，不调用 ASR 和笔记模型。
- **口播知识**：低画质、带音轨，沿用 ASR 与笔记流程。
- **画面知识**：高质量素材先转写，保留视频并标记待 OCR；本次未实现 OCR 引擎。
- **待确认用途**：元数据不足时进入 `review`，暂不下载；在控制台作品详情选择用途后继续。
- **视频和笔记**：控制台可手动选择，保存高清并生成笔记。

视频收藏使用 `DUST_SAVED_MEDIA`（默认 `~/.dustoff/saved-media`），独立于临时缓存，默认上限 1 GiB，可在设置修改；达到上限暂停新增处理，不自动淘汰收藏。临时缓存仍为最多 1 GiB，最低空闲仍为 10 GiB。已知待 OCR 的素材也不会随转写完成而清理。
控制台可查看判断理由、修改用途和打开本地视频。已建基线后，普通或定时运行即使新收藏扫描失败，也会继续已有待办，并单独提示扫描问题。已完成的历史条目不会自动重跑；本次启用范围内的作品可手动修改用途后重新入队，既有成果不主动删除。笔记模型和 ASR 继续使用原配置。

详见 [用途分流实现与验证](docs/用途分流实现与验证-2026-09-16.md)。下面旧章节若描述“所有视频统一低码率并转写”，以本节为准。

## 快速开始

```bash
# ① 一次性：扫码登录（弹出 Chrome，用抖音 App 扫码）
node scripts/login.mjs

# ② 一次性：装配置
cp dustoff.conf.example ~/.dustoff/dustoff.conf   # 按需修改

# ③ 首次初始化：全量拉到外接盘（约 59 分钟）
node sync.mjs --init

# ④ 日常增量：一条命令，逐条串行走完三段（约 4 分钟 / 20 条）
node run.mjs
```

也可以按阶段单独跑 —— 三个入口平级、互不调用，只通过账本对话，各自幂等：

```bash
node sync.mjs        # ① 采集：扫收藏夹 → 下载        约 28 秒
node extract.mjs     # ② 提取：归档 → 备份 → 清理 → 转写   约 1.4 秒/条
node notes.mjs       # ③ 提炼：转写稿 → LLM 写笔记     约 20 秒/篇
```

**两种编排服务的是两件不同的事**：`run.mjs` 是日常增量（串行，简单，不用管限流）；分阶段跑是存量补录用的 —— CDN 签名地址 3~24 小时就过期，5831 条串行要 39 小时，跑一半地址全废，所以存量必须「趁地址新鲜批量下完，再慢慢转写提炼」。

**两种模式不需要改配置。** 配置文件里两套值都写好，命令行选用哪套 —— 带 `_INIT` 后缀的键只在 `--init` 时生效：

```bash
DUST_MEDIA=~/.dustoff/media                  # 日常
DUST_MEDIA_INIT=/Volumes/YourDisk/dustoff-media   # --init
DUST_SCAN_COUNT=200                          # 日常
DUST_SCAN_COUNT_INIT=99999                   # --init，扫到底
```

### sync.mjs 的其他用法

```bash
node sync.mjs --dry-run          # 只报计划，不下载
node sync.mjs --list             # 列出最近的运行记录
node sync.mjs --resume <run-id>  # 重试某次的下载，不重新扫描
```

`--resume` 是为初始化准备的：全量要跑近一小时，万一中途断了，拿那次存下的 `coll.json` 直接续下载即可，不用重扫（前提是 CDN 地址还在有效期内）。

### run.mjs 的其他用法

```bash
node run.mjs --limit 5      # 本轮最多处理 5 条
node run.mjs --no-scan      # 跳过扫描，消化账本里已下载/已转写的积压
node run.mjs --skip-notes   # 只做到转写为止（提炼指令还在改的时候用）
node run.mjs --scan 400     # 本轮扫多少条
node run.mjs --dry-run
```

**为什么串行而不是三段各自并发。** 20 条一天，串行约 4 分钟、分段并发约 2 分钟 —— 差两分钟，发生在凌晨没人等的时候。而串行白送四样：限流彻底不用管（并发 1 = 最多 1 QPS，三个并发上限至今没实测过）；ffmpeg 的 `spawnSync` 不再阻塞别人；止损闸变精确（串行下「连续 3 条失败」是真的连续）；日志是一条线性叙事。

**它同时持有三把锁**（`.lock.collect` / `.lock.extract` / `.lock.notes`）。不这么做的话 `extract.mjs` 能同时起来，两边捞到同一批条目，对同一条视频付两次 ASR 的钱。

**每一步做完立刻写账本**，按状态驱动 —— 昨天断在半路的今天接着走，已经下载过的跳过下载。串行流式和分三段在可恢复性上是等价的，靠的就是账本。

### extract.mjs 的其他用法

```bash
node extract.mjs --limit 5        # 只转 5 条
node extract.mjs --id <视频ID>    # 只转指定的一条
node extract.mjs --dry-run        # 只报计划
node extract.mjs --archive-only   # 只做归档补课，不转写
node extract.mjs --backup-only    # 只做转写稿备份
node extract.mjs --keep-days 30   # 临时改保留期
node extract.mjs --force          # 无视失败计数，重试标 failed 的
```

### notes.mjs 的其他用法

```bash
node notes.mjs --out /tmp/试跑     # ★ 试跑：写文件但不碰账本
node notes.mjs --stale            # 只重跑还停在旧版提炼指令的
node notes.mjs --effort low       # 换思考档位做对照
node notes.mjs --rename           # 允许文件名跟着新标题变（默认不变）
node notes.mjs --limit 3 --dry-run
```

`--out` 是打磨 prompt 时最常用的。**它写文件但不写账本**——改一版重跑一批，不用手工清现场，条目也不会被误标成已提炼。

`--stale` 靠账本里的 `prompt_hash`（提炼指令的 sha256 前 8 位）认版本，改完 prompt 精确捞出没重跑的那些，不必整批重来。

**文件名认第一次，不跟着标题走。** 实测同一条视频两次生成，10 篇里 8 篇标题不一样；文件名跟着变的话每次重跑都会在知识库里留下一堆孤儿文件。想改名才加 `--rename`。

## 脚本一览

**四个入口**（根目录）——三个阶段，外加一个把它们串起来的编排。
三个阶段平级、互不调用，只通过账本对话，所以入口放在根目录，跟被调用的零件分开。

| 入口 | 作用 |
|---|---|
| `run.mjs` | 日常增量的编排：扫一次，逐条串行走完下面三段。**不是第四个阶段** —— 它 import 下面两个入口的单条流程，共用同一本账本 |
| `sync.mjs` | ① 采集：扫收藏夹 → 下载 → 写账本 |
| `extract.mjs` | ② 提取：归档 mp4 → 备份转写稿 → 清理过期的 → 转写成文字 → 写账本 |
| `notes.mjs` | ③ 提炼：读转写稿 → LLM 写笔记 → 写账本 |

以下都在 `scripts/` 下，是被入口调用的零件（或独立的小工具），不是入口。

**批量路径**（收藏夹 → 下载）

| 脚本 | 作用 |
|---|---|
| `login.mjs` | 有头 Chrome 扫码登录，登录态存进固定 profile。一次性 |
| `get_collection.mjs` | headless Chrome 复用登录态，CDP 截收藏夹接口，输出含播放地址的 JSON；同时用每页的 `cursor` 还原收藏时刻 |
| `download.mjs` | 吃上一步的 JSON，并发下载最低码率档，校验后落盘 |

**库**（不单独运行）

| 脚本 | 作用 |
|---|---|

## 实现要点

**不逆向签名，让真浏览器替我们签名。** 抖音的 web 接口需要 `a_bogus` 等签名参数，自己实现很脆弱（GitHub 上 15k star 的同类项目 README 里自己写着「加密参数算法已过期失效」）。本项目启动系统 Chrome，用 CDP 截获页面自己发出的接口响应 —— 抖音要打掉这条路，得先打掉自己的网页版。

**批量流程只启动一次浏览器。** 收藏夹接口 `listcollection` 的响应里已经带了 `play_addr` 和 12 档 `bit_rate`，所以扫描时一并提取，下载阶段全程 `curl`，不再逐条起 Chrome（那样 5000 条要多花约 8 小时）。

**下低码率档，但必须带音轨。** 只要内容不要原件，所以不下默认的 `play_addr`。但**不能无脑取最低档**——实测 58% 的视频，最低那几档是纯视频没有音轨，而后半段靠 ASR 提取内容，没音轨等于白下。

规律是同一个 `gear_name` 会在 `bit_rate` 里出现两次，高码率那个比低码率的多约 55 kbps，那 55 kbps 就是音频轨。但这规律不通用（有些视频档位互不重名且最低档就带音频），而 `audio_bitrate` 字段两类视频上都可能缺失。所以策略是：**按规律优先猜带音轨的档 → 下载后 `ffprobe` 验证 → 验不过回落 `play_addr`**（网页播放器用的地址，必然有音轨）。

实测 31 条全部拿到音轨，回落一次都没触发，体积只比「无脑取最低档」多 18%。

**CDN 地址有时效。** 地址路径第二段是十六进制的过期时间戳，实测 3~24 小时不等。下载前会先判断，过期直接跳过并提示重扫，不做注定 403 的无用请求。因此**扫描与下载不能隔太久**。

**超长视频不下。** 短视频的时长极度长尾：实测样本中位 58 秒，最长的一条却有 841 分钟。超长的多是合集、解说、全片，做知识笔记价值低却吃掉大量体积。默认拦下超过 10 分钟的——实测只影响 4.6% 的条目，却省约 12.6 GB。被拦下的不丢弃，会计入汇总并列出最长的几条，想要的可以单独捞。

**下载四重校验。** CDN 失败时常返回 HTTP 200 的错误页，只看状态码会把 HTML 当 mp4 静默写入。所以要求：`curl --fail` + 文件 > 10 KB + `file --mime-type` 是 `video/*` + `ffprobe` 确认有音轨，四关全过才算成功，否则换下一个地址或回落 `play_addr`。

## 已定的技术选型

三段的选型都已经用实测数据定下来了，不必重新论证。

**转文字用云端 ASR，不用本地 whisper。** 同一条视频、真值取自画面硬字幕，云端 ASR 错 1/8，本地 `whisper base` **错 8/8**（Claude Code→Cloud Code、图表→图标、时序图→实序图、重绘→重惠…）。**whisper 已淘汰**，不留作兜底。

**模型是 `qwen-audio-3.0-asr-flash`**，走同步 `multimodal-generation` 端点，音频 base64 内联。同价的 `qwen3-asr-flash` 也支持，改 `DUST_ASR_MODEL` 即可切换——两族的请求与返回差异隔在 `extract.mjs` 的 `DIALECTS` 里。选型全过程见 [`docs/ASR选型-2026-09-02.md`](docs/ASR选型-2026-09-02.md)。

**热词不只提准确率，也管输出格式。** `~/.dustoff/asr-context.txt` 里的词会被优先识别：不给热词认成 `cloud code`，给了就是 `Claude Code`；且**在表里的缩写输出干净（`SVG`），不在表里的会被拆成字母（`S V G`）**。想到新词随时加。

**单价 ¥0.00022/秒**（华北2，已核实；≈¥0.79/小时）。按收藏夹真实分布算：日常增量 **¥0.28/天 ≈ ¥8.4/月**，存量全量约 **¥109** 一次性。`qwen-audio-3.0` 另有 10 小时免费额度（到 2026/10/27），够用 28 天日常增量。

**300 秒是硬上限**，超了自动按静音中点切片（占 9%，实测接缝不劈词）。异步端点（`fun-asr`）不限时长但故障面从 1 处涨到 8 处，这段代码跑在凌晨无人值守，不划算。

**OCR 暂缓，但迟早要加回来。** ASR 拿不到屏幕上的文字——实测一条屏幕录制视频，ASR 171 字 vs OCR 9396 字。完整依据与实现方案见 [`docs/待办-OCR增强.md`](docs/待办-OCR增强.md)。

**提炼用智谱 GLM-5.3-Flash，走 OpenAI 兼容端点。** 裸 `fetch` 就能调，和第二段调 DashScope 的写法一致，项目继续零 npm 依赖。实测 12 条真稿写出 10 篇，¥0.032——**改一版 prompt 全批重跑只要二十秒和三分钱**，这是把「材料够不够、归哪个分类、时效多久」这些会变的判断都放在第三段的前提。

**`reasoning_effort` 必须显式传。** 三个实测出来的坑：参数名是 `reasoning_effort`，写成 `thinking:{effort}` 不报错但被静默无视；**不传不是「用默认档」，实测走的是 `max`**，思考 token 从均值 28 涨到 1426，HTTP 200、结果照样对，只有账单变厚；思考 token 计入 `max_tokens` 且按输出计费，调小了会思考到正文为空还返回 200。`medium` 是硬错误（400）。

**分类先让 AI 自由填，不给固定选项。** 原本定的四类（AI技术 / 游戏攻略 / 生活方式 / 其他）按样本粗分约 28% / 6% / 11% / 55%——**一个分类体系里最大的桶叫「其他」，说明这个体系是错的**。攒够约 200 条看真实分布再锁列表。

**时效性按条打标，不按类目一刀切。** 同样是游戏攻略，网游会过期、单机不会。建议四档：`none`（菜谱/摄影技巧/单机攻略/原理方法论）、`slow`（1-3 年，框架用法）、`fast`（6-12 月，模型对比/API 用法）、`event`（时点绑定，网游版本/活动/新闻）。判定放在元数据阶段，零转写成本。

**暂不上 RAG / 向量库。** 首轮 AI 类约 1300 条 markdown，`grep` 完全够用；知识库最常见的查询是「我记得存过一个讲 XX 的」——这是关键词检索，向量库反而不准。等 `grep` 真不够用了再上。

**存量处理的量级**（以约 5800 条的样本为例）：约 5000 视频 + 800 图集，视频总时长约 244 小时。OCR 按实测 3.0× 实时算，全量约 81 小时；只做 AI 类 + 2025 年起约 21.6 小时，并发 4 路可压到约 7 小时。

## 已知限制

- **笔记还没正式入库**。第三段跑通了，但一直在 `--out` 试跑模式下，账本里还没有一条 `extracted`。提炼指令定稿后才切换。
- **已知的笔记质量问题**：10 篇里 6 篇比原文还长。长转写稿能压到 45~67%，短的却胀到 154~281%（309 字 → 869 字）——材料薄的时候模型在凑字数。
- **`collected_at` 现有条目全空**。还原收藏时刻的代码是后加的，值只有新扫一轮才拿得到；在那之前笔记的 `收藏日期` 会回退到首次扫到的时间。
- **图集不下载**。约占收藏的 14~33%，能正确识别并跳过，但没有处理路径。
- **超过 10 分钟的视频不下载**（可配置）。拦下的会列在汇总里，需要时用 `node scripts/fetch.mjs '<链接>'` 单独下，或 `DUST_MAX_DURATION_MIN=0` 临时放开。
- **无扫描层增量**。每次都扫固定条数，靠下载层的文件缓存去重 —— 结果正确，但每次白扫已知条目。
- **登录态约两个月过期**，需要重新扫码。守卫会提前 7 天预警。
- **依赖抖音网页版结构**。收藏页的滚动容器、接口路径若变更需要跟进。

```
└── YYYY-MM-DD-<主题>.md     最终笔记。日期是**收藏日期**，不是发布或提炼日期
```

**文件名用收藏日期**，因为回头找的时候记得住的是「我大概那阵子存的」。笔记里三个日期都有：`发布日期`（作者什么时候发的）、`收藏日期`（我什么时候存的）、`提炼日期`（这篇笔记什么时候变成现在这样的——prompt 改一版就会变，这正是它的价值）。

**刻意放在 dustoff 之外。** 工具会被换掉、重写、废弃，知识不该跟着走；而且将来扩展其他平台时，知识库该是各来源的汇聚点，不是某个采集器的子目录。位置由 `DUST_NOTES` 配置。

### 关于移动硬盘

外接盘承担三件事，全部由**一个配置项** `DUST_EXTERNAL` 派生：

```
DUST_EXTERNAL=/Volumes/T7
├─ /Volumes/T7/dustoff-media   ① --init 全量下载的落点（本机装不下）
│                              ② 转写完的 mp4 归档（同一个目录）
└─ /Volumes/T7/dustoff-text    ③ 转写稿备份
```

换盘（T7 → T8）只改这一行。原先三处各写一遍完整路径，漏改一处不会报错——**会一半文件去新盘、一半去老盘，而老盘没插时那一半只会安静地跳过**。

| 场景 | 量级 |
|---|---|
| 日常增量 | 约 61 MB/天；转写完搬走或 7 天后删，本机稳态约 430 MB |
| 首次初始化 | 全量可达数十 GB，本机多半装不下 |
| 长期归档 | mp4 约 16.5 GB/年 · 转写稿约 35 MB/年 |

**mp4 和转写稿的保护方式相反，是故意的。** mp4 是**移动**（本地不留），转写稿是**复制**（本地必须留着，第三段每次提炼都要读）。理由是体积和可再生性正好反着：mp4 一年 16.5 GB 但可以重下，转写稿一年 35 MB 却是花钱买的，全量重转约 ¥109。**保护力度该跟体积反过来。**

**没插盘就跳过，插上那轮补齐。** 归档不是只处理本轮刚转的——每轮都从账本全量扫一遍，把之前因为没插盘而错过的一并搬走。所以不会有视频因为「归档那天盘没插」而在第 7 天被删掉。

**判断「盘插没插」用设备号，不是路径存在性。** 这是这一节唯一的技术难点：macOS 上外接盘没挂载时，`mkdir -p /Volumes/T7/xxx` 会在**启动盘**上真的建出这个目录，程序会兴高采烈地把 mp4「移到外接盘」，实际全写进内置盘；而 T7 真插上时系统会把它挂到 `/Volumes/T7 1`，文件永远留在那个假目录里。所以判据是「这个路径的 `st_dev` 跟 `/` 一不一样」——一样就说明盘没挂载，直接跳过，**绝不建目录**。

**跨盘搬不是原子操作**，所以是「复制 → 核对整个目录的文件数和总字节 → 删原件」。核对时跳过 macOS 的 `._` 伴生文件（exFAT 不支持扩展属性，macOS 会给每个文件额外配一个）。中途出任何岔子都只留在本地——**宁可没搬走，不能搬丢**。

> exFAT 的簇很大（实测 256 KB），而转写稿单个只有 1.7~8 KB，所以外接盘上的占用会比实际数据大几十倍（23 个文件、156 KB 数据，占了 5.8 MB）。按一年 7200 个文件算约 1.8 GB —— 在 500 GB 的余量上无所谓，知道就行。
